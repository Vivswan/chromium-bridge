# 威脅模型

chromium-bridge 保護什麼、防範誰, 以及它明確不防禦什麼。與 [trust-boundaries.md](trust-boundaries.md) 和[工具風險矩陣](tool-risk-matrix.md)搭配閱讀。

請先閱讀[安全標準線](security-bar.md): 它說明這些機制承諾了什麼, 而本頁負責說明每一項如何落實。

## 資產

- 使用者的**已驗證瀏覽器工作階段** (cookie, 包含 httpOnly; 網頁儲存空間中的權杖) - 也就是在使用者已登入的網站上*以使用者身分*行動的能力。
- 使用者能看到的**頁面內容**。
- 以使用者身分**執行動作** (點擊 / 填寫 / 導覽 / eval) 的能力。
- **線路協定**的完整性 (損毀的串流可能讓橋接器掛起或當機)。

## 參與者

| 參與者 | 受信任? | 說明 |
|-------|----------|-------|
| 使用者 | 是 | 擁有這台機器與 Chrome 設定檔 |
| MCP 用戶端 (Claude Code、Codex、...) | **是, 設計使然** | 由使用者設定; 由它驅動工具 |
| Rust 執行檔 (MCP 伺服器 + 原生訊息主機) | 是 | 我們要保護的對象 |
| MV3 擴充功能 | 是 | 但與不受信任的頁面程式碼並行執行 |
| **網頁** | **否** | 可能受攻擊者控制; 可能藏有提示注入 |
| 其他本機使用者 / 程序 | **否** | 可能嘗試連上橋接 socket |
| 網路 | 不在範圍內 | 沒有遠端介面 - 一切都在 localhost / stdio 上 |

## 信任假設

- **單一使用者的機器。** 橋接器是一個 0600 的 Unix domain socket (沒有監聽埠), 位於 0700 的每使用者目錄中, 由核心的對端 UID 檢查、由核心證明的執行檔身分, 以及基於每次執行秘密的 HMAC 挑戰回應所把關; 模型假設沒有同 UID 的敵對本機使用者。證明還會額外拒絕*不同的*同使用者執行檔, 但無法阻止重新執行*我們自己的*執行檔的同使用者攻擊者 (見威脅 #4)。
- **MCP 用戶端受信任。** 使用者自己安裝的惡意用戶端不在範圍內 - 它已經擁有使用者授予它的一切。這些工具本來就是要給該用戶端驅動的。
- **Chrome 的沙箱與擴充功能模型成立。** 我們依賴 MV3 在內容指令碼與頁面 JS 之間的隔離, 以及 Chrome 對主機權限的強制執行。

## 主要威脅與緩解措施

1. **網頁影響代理程式, 使其在未經核准的情況下對該頁面採取行動。** -> 頁面層級的操作需要**允許清單中的來源 (origin)**; 新來源會觸發明確的使用者提示 + `chrome.permissions.request`。頁面無法把自己加入允許清單。

2. **提示注入: 頁面內容誘騙模型發出危險的工具呼叫** (例如「執行這段 eval」、「讀取 cookie 並送出去」)。 -> 對代理程式而言, 觀察到的頁面內容是*資料*, 不是指令。另外獨立地, 高風險動作 (送出 / 連結點擊、`page_eval`、關閉分頁) 需要**在擴充功能持有的視窗中取得使用者確認**, 該視窗頁面無法偽造、讀取或自動關閉, 且 `page_eval` 對**每一次呼叫**都要確認並顯示完整程式碼。這個逐動作提示只涵蓋高風險操作。低風險操作 (導覽、`page_text`、`tab_list`, 以及遮罩後的 cookie 或儲存空間讀取) 執行時沒有逐動作提示, 所以已經能觸及擴充功能的驅動方可以導覽、讀取遮罩後的頁面內容並列舉分頁, 使用者不會看到每一步。確認是對危險動作的閘門, 不是「沒有任何事會靜默發生」的保證。這些閘門預設開啟; 每一個都是有文件記載的設定, 其選擇退出的殘餘風險列表見 [SECURITY.md](../../../.github/SECURITY.md#page_eval-and-confirmation-defaults-fail-safe)。

3. **憑證 / 權杖外洩。** -> cookie / 儲存空間是**唯讀的** (沒有 set)、**限定在允許清單範圍內**, 並在離開擴充功能之前就經過**遮罩** (JWT / 十六進位 / 長數字串 / 類權杖形狀)。`storage_get` 的遮罩不可由使用者關閉。`page_text` 會遮罩密碼與類卡號數字。

4. **另一個本機程序劫持橋接器**以發出工具呼叫或讀取回應。 -> 每一個連線都要通過同使用者檢查、由核心證明的執行檔身分, 以及一次 **HMAC-SHA256 挑戰回應**, 其中每次執行的秘密從不經過線路, 且新鮮的 nonce 可擊敗重放。證明是雙向的 (主機與伺服器互相證明)。

   在 Unix 上**沒有監聽埠**: 橋接器是位於 0700 目錄中的 0600 Unix domain socket, 而**核心的對端 UID 檢查**會拒絕其他使用者。對端的身分必須與我們相符: 在 Linux 上是其 `/proc/<pid>/exe` 的 SHA256, 在 macOS 上是其執行中映像的 `cdhash`, 透過 Security 框架以其核心稽核權杖識別, 因此*不同的*同使用者程式在能夠驗證之前就被拒絕。

   在 Windows 上, 橋接器是一條具名管道, 其安全描述元只允許目前使用者 (核心在開啟時強制執行), 且兩端互相證明對方的映像: 核心為管道對端記錄的 pid、它所執行映像檔的 SHA-256, 以及對用戶端程式 (harness) 而言其 Authenticode 發行者。按路徑量測是下方列出的一項殘餘風險。

   鎖定檔在 Windows 上沒有明確的模式, 依賴每使用者執行階段目錄的預設權限 (`LOCALAPPDATA`, 或 `USERPROFILE\AppData\Local`; 作為最後手段的暫存目錄不保證是每使用者的; 見 `src/packages/core/src/ipc/` 中的 `runtime_dir()`)。

   **未涵蓋:** 重新執行*我們自己的*執行檔的同使用者攻擊者, 與合法主機逐位元組相同 (相同雜湊、相同 cdhash), 所以雜湊與程式碼簽章都無法區分兩者。登記儀式 (威脅 #6) 使擴充功能與橋接器的*配對*受在場把關, 但在登記之後並不區分同使用者的程序 (見資訊清單替換的殘餘風險)。macOS 上的 Team ID 固定 (同時信任另一個獨立簽署的建置) 已延後。

5. **格式錯誤或過大的訊息讓橋接器當機或損毀。** -> Native Messaging 訊框會檢查長度 (入站 64 MB 上限, 出站 1 MB 上限); `panic = "abort"` 設定檔 + stderr panic hook 讓 panic 不會進入協定串流; 解析錯誤會被回報而非致命; 而且 cargo-fuzz 目標 (`src/packages/core/fuzz/`) 同時涵蓋線路解析器 (Native Messaging 訊框、MCP JSON-RPC、橋接與交握解碼器) 和它們背後的語意驗證器 (交握 MAC 驗證器、訊框分類器、DER 簽章解析器、Enclave 挑戰建構器, 以及資訊清單所有權判定)。

6. **靜默配對: 惡意的 `claude mcp add` (或任何能寫入 MCP 用戶端設定的程序) 在使用者未察覺的情況下建立整條鏈路。** -> **登記儀式** (macOS 上預設開啟): `chromium-bridge pair` 在 Secure Enclave 內鑄造一把 P-256 金鑰, 其每一次使用都需要使用者在場 (Touch ID / 密碼), 並執行一次受在場把關的自我測試簽章; 拒絕它會讓機器維持未登記狀態。擴充功能固定該公鑰, 並據此驗證 `enclave_proof` 訊框; 在未登記的機器上, 挑戰會得到 `enclave_error: not_enrolled`, 而已固定金鑰的擴充功能會失敗即關閉。重新固定 (`pair --reset`) 再次需要在場, 而 `revoke` 會刪除金鑰, 使得任何證明都無法產生。使用者比對 `pair` 印出的 SHA-256 指紋與擴充功能顯示的指紋, 這能擊敗夾在兩者之間的中間人主機。**範圍:** 這關閉了靜默的*首次*配對與靜默重新固定; 它**不**關閉登記後的同使用者替換 (見下方殘餘風險)。

7. **已撤銷的用戶端或已撤銷的主機繼續行動, 因為撤銷沒有到達強制執行點。** -> **任一側撤銷紀元**: 信任記錄 `runtime_dir()/trust.json` 中的一個計數器, 每個強制執行點都會重新讀取整份記錄。用戶端撤銷與緊急開關 (kill switch) 的狀態轉換都落在遞增該計數器的那一次 `trust.json` 寫入中; 主機金鑰撤銷則是一次鑰匙圈刪除, 加上在同一把執行階段鎖下另一次盡力而為的紀元遞增, 遞增失敗會在下一次金鑰驗證時浮現。`revoke-client` (來自 CLI 或擴充功能經主機中介的 `client_revoke` 訊框) 會改寫允許清單並遞增紀元; 然後執行中的中介 (broker) 的每請求准入閘門及其閒置連線監看器會以失敗即關閉的方式斷開被撤銷的用戶端程式, 並拒絕其重新接入。主機金鑰的 `revoke` / `pair --reset` 會刪除 Enclave 金鑰並遞增紀元; 原生訊息主機確認金鑰已從鑰匙圈消失, 並推送一個主機發起的 `enclave_revoked` 訊框, 因此已固定金鑰的擴充功能會失敗即關閉, 無需等待選用的重新驗證。現在從任一側解除配對都會刪除憑證的「兩半」(擴充功能的撤銷也會要求主機刪除其金鑰, 並持久重送直到被確認)。紀元是變更通知, 從來不是權威: 竄改它的同使用者寫入者可以強迫一次假的推送, 或讓每次讀取都失敗即關閉, 但無法讓已配對清單或鑰匙圈不認可的任何人獲准進入。**範圍:** socket 這一段是即時的; 擴充功能對主機金鑰撤銷的反映, 最晚在下一次 Service Worker 喚醒時完成。已遭入侵但仍在允許清單上的用戶端在被撤銷前仍受信任 (證明識別的是執行檔, 不是意圖)。被替換的原生訊息主機 (威脅 #4 的資訊清單替換殘餘風險) 可以偽造 `enclave_revoked` 推送, 讓已固定金鑰的橋接器失敗即關閉, 這是對使用者自己的橋接器的阻斷服務, 不授予任何能力, 也無法在使用者空間以驗證手段消除。

## 明確的非目標

- 防禦已遭入侵的作業系統帳戶, 或執行*我們自己的*執行檔的同使用者攻擊者。對端 UID 與執行檔證明會拒絕其他使用者和其他執行檔, 但執行正版執行檔的同使用者程序與合法主機逐位元組相同, 對 IPC 層而言仍在範圍之外 (見威脅 #4)。
- 防禦使用者自己設定的惡意 MCP 用戶端。
- 多使用者 / 共用機器的隔離。
- 遠端攻擊者 (沒有遠端攻擊面)。

## 殘餘風險 (已接受、已追蹤)

- **Native Messaging 資訊清單替換 (主機到擴充功能這一跳未經驗證)。** 橋接器以對端 UID 檢查、證明和 HMAC 驗證主機到伺服器的 socket 這一跳, 但沒有任何機制向擴充功能驗證原生訊息主機。主機資訊清單位於使用者可寫入的目錄, 所以同使用者攻擊者可以改寫其 `path`, 把瀏覽器指向惡意的主機執行檔。瀏覽器隨後啟動該執行檔, 它直接以 Native Messaging 與真正的擴充功能對話, 發出 `BridgeReq` 而完全不碰經驗證的 socket。`allowed_origins` 固定了哪個擴充功能可以開啟主機, 但沒有任何東西固定擴充功能會接受哪個主機。登記儀式縮小了這個問題: 有了擴充功能側的固定金鑰, 被替換的主機無法在不引發使用者意料之外的 Touch ID 提示的情況下出示有效的 `enclave_proof`, 所以*登記時*的替換不再是靜默的。仍然開放的是在場檢查*之間*的替換: MV3 在每次 Service Worker 重啟時 (大約每閒置五分鐘一次) 重新產生主機, 無法在每次重新連線時都要求在場 (每五分鐘一次 Touch ID 提示無法出貨), 而任何靜默的每次重連憑證都能被任何同使用者程序動用。因此在登記之後, 換掉資訊清單或重新執行我們執行檔的同使用者攻擊者, 在重新連線時無法區分。選用的逐動作在場層級 (另行追蹤) 是能關閉這個剩餘部分的機制。
- **已核准來源上的讀取外洩 (已接受)。** 一旦某個來源進入允許清單, 讀取依設計不再提示: `page_text`、`cookie_get` 和 `storage_get` 執行時沒有逐動作確認, 只受啟發式遮罩保護。因此在已核准、已登入的來源上成功對模型進行提示注入的頁面, 可以靜默讀取頁面內容, 以及遮罩啟發式漏掉的任何秘密 (它們比對的是類權杖的形狀, 不是語意, 所以新穎的格式可能漏網)。曾考慮並否決了把讀取放到逐動作提示之後: 那會給幾乎每一步代理程式操作都加上一次確認, 教會使用者對守護真正危險動作的提示也一路點過去。這是有意識接受的殘餘風險; 緩解措施是來源允許清單 (頁面必須已經位於使用者核准的地方)、作為盡力而為層的遮罩, 以及稽核日誌。
- **高風險點擊寬限期**讓*無關的*同來源程式碼不必重新提示即可執行: 一次送出或連結點擊獲准後, 同一來源與同一動作類型在 60 秒內跳過確認。`page_eval` 不在這個寬限期內; 它每次呼叫都重新確認。
- **信任狀態隔離有一個冷啟動窗口 (#32)。** 登記固定金鑰、已遭入侵標記、強制執行的策略狀態 (策略棘輪與切換旗標) 以及允許清單都存放在 `storage.local` 中, 而 Chrome 預設會把它暴露給內容指令碼。擴充功能以 `setAccessLevel(TRUSTED_CONTEXTS)` 把兩個儲存區域都限定在擴充功能情境中, 並在該限制生效前讓登記閘門失敗即關閉。執行階段訊息路由器 (通往同一狀態的中介路徑) 拒絕每一則發送者不是擴充功能自身頁面的訊息, 所以內容指令碼無法透過 `add_allow` 植入允許清單, 也無法透過 `get_enrollment` 讀取固定的金鑰 id / 指紋。由於 `setAccessLevel` 是非同步的, 且在 Service Worker 啟動後才套用, 冷啟動時仍有一個次毫秒的窗口, 來自前一個 worker 生命週期、位於已遭入侵渲染器中的內容指令碼, 可能在限制生效前直接把竄改過的值寫入 `storage.local`; 限制隨後把它鎖定在裡面。路由器已設閘門之後, 這個冷啟動窗口是內容指令碼通往信任狀態「唯一」剩下的路徑。沒有使用者空間 API 能關閉它; Enclave 儀式的密碼學檢查限制了、但無法抹除被植入的固定金鑰所能達成的事。
- **高風險確認現在在頁面可觸及的 DOM 之外呈現。** 每一個高風險確認 (送出點擊、`page_press`、`page_select`、`page_eval`、`tab_close`、`page_upload`) 都顯示在專用的 `confirm.html` 彈出視窗中, 那是一份位於自身程序中的 `chrome-extension://` 文件。受保護的頁面無法讀取、聚焦、覆蓋或點擊它, 而訊息路由器只接受來自那份確切文件的 ready / resolve 確認訊息。這關閉了先前的殘餘風險: 當時的快顯提示 (toast) 是畫在頁面自己的 DOM 中 (或在 CDP 下畫在其 MAIN world 中), 被提示注入的頁面可以用 `MutationObserver` 監看它並自行點擊「允許」。確認開啟期間與管線競速的導覽, 會被在頁面中與動作原子執行的來源斷言攔截, 而點擊還額外綁定到使用者核准的目標描述元。殘餘風險: 該視窗證明的是在頁面無法觸及的介面上的一次點擊, 而不是密碼學意義上的使用者在場; Secure Enclave 在場閘門為兩個最關鍵的工具關閉了這個剩餘部分, 做法是在已登記的 Mac 上把 `page_eval` / `page_upload` 的核准路由到主機的 Secure Enclave, 那裡的判定是不可偽造、由主機簽署的使用者在場檢查 (Touch ID 或登入密碼)。對於其他高風險類型、非 macOS 平台、未登記的 Mac, 以及主機策略選擇退出 `touchIdConfirm` 時 (這種放寬本身需要一次經簽署、受在場把關的策略寫入: 在已登記的 Mac 上要 Touch ID, 在未登記的 Mac 上則被拒絕), 該視窗仍是確認介面。
- **`page_upload` 可以附加呼叫者指定的任何本機檔案。** 當該工具啟用時 (預設關閉), 它會把呼叫提供的任何絕對路徑附加到檔案輸入欄位, 所以被誘導在某頁面上呼叫它的模型, 可以把使用者從未挑選的檔案交給該頁面, 例如 SSH 金鑰或私人文件。它前面有三道閘門: 選擇加入、來源允許清單, 以及顯示確切路徑的逐呼叫確認 (在已登記的 Mac 上是 Secure Enclave 使用者在場檢查; 其他情況是頁面無法觸及的擴充功能視窗)。仍然開放的是路徑本身沒有被限制在挑選的檔案或安全目錄內: 獲准的呼叫會附加它指定的任何檔案。已列入強化追蹤 (改用作業系統檔案選擇器, 讓模型不指定任何路徑), 之後才會建議一般用途使用檔案上傳。
- `page_snapshot_precise` 會短暫附加偵錯工具 (橫幅閃現)。
- **Windows 按路徑量測映像 (已接受、已追蹤)。** 管道對端的 pid 解析為映像路徑, 雜湊與簽章是從該檔案讀取的, 而不是從已映射的映像, 因為使用者模式沒有它的控制代碼。Windows 允許重新命名執行中的執行檔, 所以同使用者程序可以在啟動與量測之間在該路徑放上另一個檔案; Linux 面臨的 pid 重用競爭同樣適用。
- **Windows 用戶端程式是伺服器 stdin 管道的建立者。** 記錄中的父程序在 `CreateProcess` 時可由呼叫者選擇, 所以伺服器量測其 stdin 管道兩端所記錄的程序, 對其他任何情況 (主控台、來自兩個程序的端點) 都失敗即關閉。
- **持有用戶端程式管道端點者可以在其上執行伺服器 (Windows)。** 用戶端程式以管道式 stdin 產生的子程序, 透過繼承持有該端點, 可以啟動一個證明該用戶端程式的伺服器; 匿名管道是單向的, 所以它只能讀取用戶端程式自己的請求。對用戶端程式擁有 `PROCESS_DUP_HANDLE` 的同使用者程序也可以複製寫入端並注入請求: 這是[邊界 1](trust-boundaries.md#邊界-1-mcp-用戶端---rust-mcp-伺服器-stdio-json-rpc-20)的 stdin 寫入者殘餘風險。
- **Windows 發行者錨點跳過撤銷檢查 (已接受、已追蹤)。** `WinVerifyTrust` 在不做撤銷檢查的情況下執行, 這也是瀏覽器自家安裝程式驗證所採用的策略: 線上檢查會在離線時卡住啟動, 而只用快取的檢查會在從未抓取過 CRL 的機器上失敗。因此被撤銷的發行者憑證會保留其錨點, 直到 `revoke-client` 移除它; 以目錄簽署的映像沒有內嵌簽章, 只以雜湊作為錨點。
- **CDP 模式** (`cdpMode`, 主機持有的策略授予, 預設關閉; 啟用它是一次經簽署、受在場把關的策略寫入 - 在已登記的 Mac 上要 Touch ID, 在未登記的 Mac 上則被拒絕) 把所有頁面操作都經由 `chrome.debugger` 路由。啟用後它會**繞過頁面 CSP** (讓 `page_eval` 能在嚴格 CSP 的網站上執行), 並對該分頁保持**持續的偵錯工具附加** (「Started debugging this browser」橫幅會一直顯示)。允許清單、逐動作確認與遮罩不變; 殘餘風險是更寬的攻擊面與被移除的 CSP 縱深防禦層, 作為選擇加入的明確代價而被接受。
- **註冊修復不受在場把關。** 選項頁面的 `registration_repair` 訊框透過與 `doctor --fix` 相同的接縫重新註冊偵測到的瀏覽器: 冪等, 而且只把瀏覽器指向這個執行檔, 與 CLI 路徑姿態相同, 而 CLI 路徑也沒有閘門。遭入侵的擴充功能獲得的, 不過是任何同使用者程序本來就有的 (威脅 #4 的類別)。

### 主機持有策略的殘餘風險帳冊

主機持有策略的工作把安全策略移到了主機側: 一份經簽署的基準、一層未簽署的限制覆蓋層、擴充功能側的值棘輪, 以及每連線的分派屏障。實作審查指出了下列殘餘風險, 每一項都是刻意接受的; 各條目說明可能發生什麼、確切的前提、什麼限制了它, 以及為何接受。[SECURITY.md](../../../.github/SECURITY.md) 指向這裡, 承重的程式碼註解也是。請把這些條目放在一起讀, 而不是孤立地讀 - 它們會組合。一個實例: 第一條的界限 (只有儲存修訂版本或更高的正版基準) 錨定在儲存的棘輪記錄上, 而下方的冷啟動條目使該記錄在其窗口內可被刪除 - 錨點一旦被刪除, 該金鑰曾簽署過的最寬鬆正版基準就會以首次策略的身分套用, 不論其修訂版本。

- **一次失敗的入侵標記持久化加上 worker 重啟, 會讓屏障對被擷取的正版策略重新開啟。** 當策略推送對固定金鑰的簽章驗證失敗時, 擴充功能會同步閂住記憶體中的入侵旗標, 然後寫入持久的入侵標記。如果該持久寫入「失敗」, 且 Service Worker 隨後重啟, 新的 worker 會在未閂住、也沒有持久標記的狀態下啟動, 所以重放的正版、逐位元組相同的 `policy_current` 能通過驗證, 以冪等重放的方式推進棘輪, 並重新開啟分派屏障。前提: 一次持久儲存寫入失敗 (邊緣情況)、一次 SW 重啟, 以及一個被擷取的正版訊框。界限: 屏障只會對固定金鑰在儲存修訂版本或更高簽署過的「某個」正版策略重新開啟 - 攻擊者只能在其擷取到的文件中挑選, 無法偽造越過棘輪與簽署 touched-set 規則的新放寬 - 而主機重新證明只在使用者選擇加入定期重新驗證的情況下才進一步縮小它 (`hostReverifyMs`; 預設為 0 時沒有任何重新連線會被挑戰, 所以界限只靠棘輪成立)。在單一 worker 生命週期內, 記憶體中的閂鎖無論如何都成立。失敗的持久化會被記錄, 從不靜默吞掉 - 但在這個前提下沒有任何持久證據能留存: 稽核事件寫入的是剛剛失敗的同一個儲存空間, 而入侵事件類型是擴充功能本機的, 從不轉發到主機的稽核日誌。接受的理由: 記憶體中的閂鎖依定義無法在重啟後存活; 要完全關閉它需要「持久寫入成功才繼續」或開機時重新證明, 而不是更寬的閂鎖。
- **同金鑰復原路徑中的一個微任務窗口。** 還原被取代的已儲存策略記錄的寫入復原, 會在其還原寫入之前立即重新檢查固定金鑰重設紀元, 但 `chrome.storage` 不是交易式的, 所以在那次最後檢查與寫入之間完成的同金鑰重新配對, 仍可能看到復原動作還原了重設剛剛移除的記錄。構造上是單向的: 紀元在讀取先前記錄之前就被擷取, 所以另一側的誤觸會把還原變成移除 (失敗即關閉), 而剩下的那個方向只能復活一筆無作用的記錄, 範圍檢查會讓它在任何其他固定金鑰下都無法進入強制執行。接受: 沒有交易式儲存就無法修正。
- **單次推送的不一致, 以及與錯誤推送的驗證競速的請求。** 兩個強制執行點 (主機分派、擴充功能閘門) 可能在策略變更前後短暫不一致; 窗口是一次推送, 而擴充功能在其邊界上是權威 (主機持有策略的一個已指名後果)。另外, 策略訊框在請求閘門之前路由, 但不與請求佇列排序 (與緊急開關訊框接受的同一種 void 路由): 訊框路徑與請求路徑不共用計數器, 所以在錯誤簽章的推送抵達與其簽章驗證實際「失敗」之間 (一次訊框鏈跳躍、兩次解析、一次 base64 解碼、一次固定金鑰讀取和一次 ECDSA 驗證之後), 已經通過閘門的請求 - 複數, 沒有任何東西把它們限制在一個 - 仍可能在仍然開啟的屏障下分派。限制它的是: 執行期間的入侵閂鎖在驗證失敗的那一刻同步設定, 且每個請求會讀取它兩次 (在閘門處折入, 並在分派自己的策略讀取時再讀一次), 所以請求必須在失敗落地之前通過兩次讀取; 而漏過去的請求是在儲存的有效策略下執行的, 那是經棘輪固定的下限, 從不比使用者上次看到套用的更寬鬆。
- **會擲回例外的在場探測會拒絕該操作 - 刻意不回退到視窗。** 如果詢問「硬體在場路由是否可用」的探測擲回例外 (異常: 已遭入侵或不存在的固定金鑰會乾淨地回傳 `false`, 不會擲回), 該操作會被「拒絕」。舊版行為會回退到擴充功能視窗確認; 恢復那個回退會讓任何探測失敗都把需要硬體 (`touchIdConfirm`) 的 `page_eval` / `page_upload` 核准降級為普通的視窗點擊 - 在場階梯的不降級規則被反轉。範圍, 精確地說: 這只涵蓋「異常」(擲回) 路徑。乾淨地回報沒有硬體能力的探測仍會路由到視窗確認, 那是該狀態下有文件記載的退化介面, 不是降級。代價是異常路徑上的可用性, 從來不是能力。
- **敵對的未固定主機可以用放寬提示占據確認 FIFO。** 在沒有固定金鑰的機器上, 策略放寬會被保留等待使用者的視窗核准。對已在等待核准的推送的逐位元組相同重放 (相同基準位元組、相同覆蓋層、相同連線) 會被合併到待處理的提示上, 但候選內容「不同」的推送會各自序列化一個提示, 所以敵對主機可以讓全域確認 FIFO 一直忙碌, 只要使用者一直不回答 - 而 FIFO 是跨「所有」確認類型的全域佇列, 所以這種占據也會餓死排在它後面的 `page_eval` / `page_upload` / 點擊確認。兩點釐清, 指名如下: 合併以 JSON 字串化的覆蓋層為鍵, 所以鍵順序重排或微幅變化的限制可以擊敗它 (代價是多一次提示, 從不壓制不同的推送); 而偽造的未簽署「限制」會靜默套用, 完全沒有提示 - 這是策略設計讓步的偽造限制阻斷服務, 因為它只會移除能力。界限: 一次一個提示, 每次拒絕都有稽核, 沒有明確核准就不會放寬任何東西, 且已固定金鑰的機器不受影響 (那裡不存在核准視窗)。一個外溢, 指名如下: 語言通道共用同一條訊框通道, 所以在未固定金鑰的機器上, 排隊中的 120 秒核准提示可能延遲 `lang_choose` 的回應 - 無害, 因為本機的 `uiLanguage` 寫入已經落地, UI 在中繼之前就已經切換; 只有診斷用的 `sent` 旗標被延遲, 而且 `chooseLanguage` 在未固定金鑰的機器上本來就回傳 false。接受: 未固定金鑰的核准視窗本質上可被唯一獲准請求它的對端占據。
- **明確選擇「en」會在每次重新連線時重新提供首次配對的語言採用。** 主機的語言儲存把不存在的記錄對應到預設值 (`"en"`, seq 0), 而攜帶已儲存值的 `lang_set` 是刻意的無操作, 不會遞增任何東西 (語言通道的回音抑制規則) - 所以對從未設定過的儲存明確 `lang_set` 為 `"en"` 會讓 seq 停在 0, 主機無法區分「從未設定」與「明確設定為預設值」。因此使用者明確選擇英文的擴充功能在每次重新連線時都看到 seq 0, 每次都重送它那一個採用用的 `lang_set`, 永遠如此。界限: 每次連線一個訊框 (每連線的採用閂鎖在一條連線內就結束它), 該訊框在主機側是無操作, 而且這條通道純屬外觀 - 語言是瀏覽器持有的顯示狀態, 從不是策略, 從不是能力。按現狀接受, 不是錯誤: 把「明確設定為預設值」折入 seq 遞增, 會波及 seq 存在目的所在的回音抑制語意, 為了外觀上的收益冒真實的風險。
- **金鑰銷毀的紀元遞增是盡力而為。** `revoke` 與 `pair --reset` 在銷毀臨界區段中清除已簽署的基準並遞增主機金鑰紀元, 但紀元寫入本身可能失敗, 而在銷毀過程中簽署的首次寫入基準隨後可能落地。界限: 讓它落地仍需要一次真實的 Touch ID 觸碰 (它是使用者在場的簽署寫入), 而下一次登記在鑄造前無條件清除基準, 會在有新金鑰可與之混淆之前嘗試移除它 (那次清除本身也是盡力而為: 失敗會警告, 鑄造照常進行)。
- **損毀的入侵標記被讀成未遭入侵。** 持久入侵標記的讀取器在遇到無法解析的記錄時回傳 null, 所以損毀的標記被讀成「沒有證據」- 整個模組都如此, 遍及繼承它的八個以上讀取點, 包括登記閘門、在場能力探測, 以及配對通知抑制。直白地說: 在能寫入這個儲存空間的介面範圍內, 損毀標記就能清除入侵證據。界限: 寫入路徑被限定在 TRUSTED_CONTEXTS 儲存空間, 所以要製造這種損毀需要擴充功能情境或下方的冷啟動窗口 - 不是網頁, 也不是穩定狀態下的內容指令碼 - 而固定金鑰記錄自身的自我檢查 (其金鑰 id 必須與儲存的公鑰相符) 是內部一致性, 不是真實性, 但這確實意味著損毀的標記無法偽造或更改固定金鑰。
- **受信任儲存空間的冷啟動窗口現在也擋在策略狀態前面。** 上方 #32 殘餘風險已指名的次毫秒 `setAccessLevel(TRUSTED_CONTEXTS)` 窗口, 現在也涵蓋策略棘輪、切換旗標、持久入侵標記, 以及先前固定金鑰記錄 (`bridgePolicyPriorPin`)。同一個窗口, 更大的影響範圍 - 以及與登記閘門的一個誠實差異: 策略訊框在閘門之前路由, 而策略路徑本身不等待限制生效, 所以策略狀態依賴的是限制被及早套用, 而不是在使用時重新檢查。沒有使用者空間 API 能關閉這個窗口。
- **「已固定金鑰的擴充功能拒絕未簽署的基準」只是已固定情況下的界限。** 在擴充功能沒有固定金鑰的機器上, 核准視窗通道會在一次新鮮、明確的使用者核准之後接受未簽署的文件。現在沒有任何主機路徑會寫入未簽署的基準, 所以視窗通道自身的讓步 (驅動擴充功能頁面的軟體可以回答其提示) 就是全部的暴露面。
- **與 `cdpMode` 撤銷競速的決策可能產生短暫的偵錯工具附加。** 新 CDP 工作階段的附加在附加後策略重新檢查讀取授予之前就已解決, 所以快照到 `cdpMode: true` 的進行中決策, 在撤銷推送落地之後仍可能附加。該工作階段上不會送出任何 CDP 命令: 重新檢查會拆除它並讓操作失敗 - 誠實的附帶說明是, 工作階段層會吞掉卸離錯誤, 所以拆除是盡力而為。重新檢查刻意放在附加之後; 在附加前重新檢查曾破壞固定的附加協定順序。
- **固定金鑰撤銷會讓現有的 CDP 附加留在原處。** 由策略驅動的拆除監聽器在儲存寫入時觸發, 而撤銷路徑刻意保留已儲存的策略記錄 (它是同金鑰的反重放錨點), 所以沒有寫入會觸發, 現有的偵錯工具附加 - 及其橫幅 - 會一直存活到分頁關閉。分派屏障會立即停止所有新工作 (切換之後; 切換之前的擴充功能沒有屏障, 改為強制執行拒絕基準); 附加只能滯留, 無法行動。
- **在 Linux 或 Windows 上無法簽署任何基準策略。** 唯一的簽署金鑰是 Secure Enclave 登記金鑰, 所以在那些平台上 `policy set` 會預先拒絕, 並讓目前策略保持不變。沒有儲存基準時, 不會授予任何能力, `policy restrict` 也沒有東西可收緊。

## 重建帶來的變化: 新的信任邊界

工作區重建引入了六個上方模型中不存在的邊界, 現在全部已交付。邊界 1-3 隨中介出貨, 邊界 4 隨桌面應用程式出貨 (後來已刪除; 見下方第 4 項), 邊界 5 隨 Touch ID 在場閘門出貨, 邊界 6 隨緊急開關出貨。每一項都按交付狀態描述: 機制、強制執行點、殘餘風險。

1. **用戶端程式 -> MCP 伺服器的 stdio 准入 (已交付)。** 伺服器不再信任任何產生它的東西。在服務任何一次工具呼叫之前, 它量測其父程序的程式碼身分 - `attest_parent()` 取得 `getppid()` 並量測該 pid 的執行中映像 (macOS: 經 `SecCodeCheckValidity` 驗證的 `cdhash` 加上簽署 Team ID; Linux: `/proc/<pid>/exe` 的 SHA256) - 並與信任記錄 `runtime_dir()/trust.json` 中已配對的用戶端比對。強制執行者: MCP 伺服器在啟動時 (`admit_own_harness`), 以及中介對每一次中繼接入再次執行 (中繼在 `AttachRequest::Client` 中回報其經證明的父程序身分, 之所以可信, 是因為中繼連線本身已通過 `attest_peer`, 因此是我們自己的執行檔)。強制執行與登記儀式一樣是選擇加入的: 尚未配對任何用戶端意味著未登記, 不強制准入, 每次啟動都以 ERROR 層級記錄 (既有的威脅 #4 同使用者殘餘風險, 不變)。一旦配對了某個用戶端, 所有不相符者都失敗即關閉 - 包括無法量測的身分, 也包括無法讀取或損毀的記錄 (載入錯誤從不被視為未登記)。授權以經證明的錨點為鍵 (有簽署時用程式碼簽署者, 否則用映像雜湊); 自我宣稱的用戶端名稱 (`CHROMIUM_BRIDGE_CLIENT_NAME`) 只是日誌標籤。殘餘風險: stdio 是沒有核心對端憑證的匿名管道, 所以這證明的是誰*產生了*伺服器, 而不是誰寫入其 stdin。啟動時 `getppid` 指向真正的產生者 (作業系統剛剛 fork 了我們), 之後的父程序重新指派會讓它指向收割程序 (reaper), 這會讓准入失敗即關閉; 但匿名管道的寫入端可以被繼承或轉交, 所以產生者與 stdin 寫入者無法證明是同一個, 而以 pid 為鍵的量測帶有常見的微秒級 pid 重用競爭 (在 macOS 上, 執行中的映像仍經簽章驗證)。它提高了門檻; 它不是對管道的核心證明。而且證明識別的是執行檔, 不是意圖: 受信任但已遭入侵的用戶端程式仍然受信任。由對抗性測試 A14 / A15 / A16 實際演練。

2. **參考計數的中介 (已交付)。** 第一個 MCP 伺服器實例綁定 0600 socket 與鎖, 成為中介; 之後經證明的實例以中繼身分接入, 而不是對擁有者送 SIGTERM (舊的「最新者勝出」`supplant_prior_server` 接管已移除)。一個共用的 `Session` 持有瀏覽器連線, 並多工處理每個已接入用戶端程式的工具呼叫。

   中介以用戶端程式類的用戶端做參考計數 (其自身的 stdio 用戶端程式加上中繼; 瀏覽器刻意不計入), 並在最後一個用戶端程式卸離時結束。關閉協定經 loom 做模型檢查 (恰好在計數為零時關閉, 終局決定之後不再有接入)。

   由中介程序強制執行: 每一次接入都個別受同使用者檢查、`attest_peer`、HMAC 交握、必須宣告角色的接入訊框, 以及 (對中繼而言) 允許清單決定所把關; socket 在 0700 執行階段目錄中保持 0600。

   DoS 姿態: 最多 8 個用戶端程式類的用戶端與 16 個不同的瀏覽器, 最多 32 條交握中的連線, 10 秒的交握 + 接入讀取逾時 (對已獲准、正當閒置的連線解除), 以及每中繼的權杖桶速率限制 (突發 128, 每秒補充 128), 會丟棄氾濫的中繼。

   殘餘風險: 中介把原本分開的影響範圍聚合在一起 (一個程序面對所有用戶端), 上限緩解了但未消除這一點; 而且它是單一故障點, 其當機會讓每個已接入的用戶端程式收到 EOF (倖存者重啟後選出新的中介, 由混沌測試 C4 / C9 演練)。

3. **主機允許清單的寫入者 (已交付)。** 受信任用戶端集合持久化在信任記錄 `runtime_dir()/trust.json` 中, 與緊急開關閂鎖並列: 0600, 在執行階段鎖下原子寫入, 以失敗即關閉的方式解析 (`deny_unknown_fields`、版本檢查、大小上限)。寫入者: CLI (`pair-client`、`revoke-client`), 以及擴充功能透過主機中介的 `client_list` / `client_revoke` 控制訊框。`pair-client` 會取代同名項目 (重新簽署後雜湊錨點的重新配對路徑); `revoke-client` 即使清單清空也保留清單 (空清單表示已登記且鎖定, `null` 表示從未配對), 並在遞增紀元的同一次原子寫入中完成, 所以執行中的中介會拒絕被撤銷用戶端的下一次請求及其重新接入。強制執行者: 0700 執行階段目錄上的檔案權限、原子寫入紀律, 以及每次准入與工作階段內請求時重新讀取記錄。殘餘風險: 信任記錄繼承與 Native Messaging 資訊清單相同的同使用者寫入者暴露 (威脅 #4 的類別) - 能執行我們 CLI 的同使用者程序可以把自己配對進去。刪除 `trust.json` 會回到記錄 ERROR 的引導狀態: 這是無法再縮減的同使用者殘餘風險, 因為沒有任何使用者空間標記能在一個可以刪除我們能寫入的任何檔案的寫入者面前存活。

4. **應用程式作為核發者 (已退役)。** 桌面應用程式已刪除, 連同其程序內的確認下限; CLI 是唯一的核發者介面, 透過 `core` 的寫入路徑與上述受在場把關的儀式。

5. **Touch ID 確認介面 (已交付)。** 最關鍵工具 (`page_eval`、`page_upload`) 的確認從頁面可觸及的 DOM 移到主機側的 Secure Enclave 使用者在場閘門。這為那些工具關閉了上方「快顯提示可被它所守護的頁面擊敗」的殘餘風險。強制執行者: 在已登記金鑰上的一次 Secure Enclave 簽署操作, 其 `kSecAccessControlUserPresence` ACL 強制要求 Touch ID (或登入密碼), 沒有即時的使用者動作就無法完成; 擴充功能以其固定的金鑰, 在專屬於在場的簽署網域上驗證所得簽章。刻意「不是」LocalAuthentication 的 `LAContext.evaluatePolicy`, 經量測它會在沒有新的使用者互動下回傳成功, 因此不能證明在場。頁面與擴充功能可以請求提示, 但無法滿足它, 而擴充功能視窗對這些類型只做顯示 (沒有「允許」按鈕)。殘餘風險: 僅限 macOS 且已登記; 其他平台與未登記的 Mac 退化為 DOM 之外、失敗即關閉的擴充功能介面, 比頁內快顯提示好, 但不具備同等的不可偽造性。逐動作 Touch ID 是主機持有的策略欄位 (`touchIdConfirm`, 預設開啟): 選擇退出會讓那兩種類型回到視窗確認, 而這是一種放寬, 本身需要一次經簽署、受在場把關的策略寫入。提示疲勞是真實的代價, 也正是為什麼只有風險最高的工具才路由到這裡。

6. **全域緊急開關與稽核日誌 (已交付)。** 一個閂鎖 (信任記錄 `runtime_dir()/trust.json` 中的 `killed`, 與紀元遞增一起原子翻轉) 從任何受信任介面停止所有橋接活動: CLI (`kill`)、擴充功能 (主機中介的 `kill_engage` 控制訊框; 擴充功能的 `kill_release` 已退役 - 主機拒絕它, 並記入稽核)。在四個層級獨立強制執行, 因此沒有任何單一檢查是承重的: 來自每個用戶端程式的每一次 `tools/call` 都在共用分派器以穩定的 `BRIDGE_KILLED` 代碼拒絕; 中介的監看器在一個節拍內切斷每一條執行中的瀏覽器連線, 且瀏覽器接入在准入時被拒絕; 在已啟用緊急開關 (或記錄無法讀取) 時啟動的原生訊息主機從不撥接中介, 只服務控制平面, 這正是讓狀態查詢、啟用與策略拉取保持可達的原因; 而擴充功能自己的閘門依其僅限 SW 的鏡像拒絕。解除是明確的, 從不自動, 僅限 CLI, 且需要使用者在場的證明 (`kill::release` 要求一個只有 `src/packages/core/src/presence/` 能建構的 `PresenceAttestation`): 在已登記的 Mac 上是一次 Secure Enclave Touch ID 觸碰; 沒有 Enclave 金鑰時, 是在真實終端機上輸入的確認 (管道式 stdin 會被直接拒絕)。硬體拒絕從不回退到下限, 驗證失敗或不可用都會讓開關維持啟用。兩種轉換在記錄無法讀取時都拒絕 (從未知狀態解除會失敗即開啟)。與此同時, 每一個安全決定 - 准入、拒絕、顯示 / 允許 / 拒絕的確認、各介面的撤銷、緊急開關轉換、工具呼叫 - 都記錄到 stderr 與有上限的 0600 `audit.log` (嚴格解析的 JSON 行, 大小上限輪替), 由 `chromium-bridge audit` 讀取, 而擴充功能自身的事件則鏡像到 #32 之後的有上限環形緩衝區, 供唯讀的選項面板使用。日誌嚴格遵守「先決定後記錄」, 永遠不會讓決定失敗 (失敗即丟棄, 附帶可見的計數器)。殘餘風險: 閂鎖共享信任記錄的同使用者寫入者暴露 (同使用者程序可以解除開關, 正如它可以刪除記錄 - 威脅 #4 的類別); 在場下限 (用於沒有 Enclave 金鑰時) 證明的是意圖而非硬體 (同使用者程序可以驅動 pty), 所以它阻止的是靜默、腳本化與意外的解除, 而不是那個敵對程序 - 每一次解除都連同授權它的階梯層級一起稽核; 啟用時對進行中工作有一個有界的次秒窗口 (一個監看器節拍), 之後被切斷的 socket 會把它們排空; 而稽核日誌依設計是盡力而為, 所以損壞的接收端會產生可見的缺口, 而不是被阻斷的決定。
