# 信任邊界

整個系統橫跨三個程序與四個協定跳點。每個跳點都是一道信任邊界 - 跨越它的資料都會被驗證和/或認證。與[威脅模型](threat-model.md)搭配閱讀。

```
MCP client --(1)-> Rust MCP server --(2)-> native host --(3)-> extension --(4)-> web page
   (trusted)         (trusted)           (trusted)         (trusted)        (UNTRUSTED)
```

## 邊界 1: MCP 用戶端 <-> Rust MCP 伺服器 (stdio, JSON-RPC 2.0)

- **協定引擎**: 此邊界上的 JSON-RPC/MCP 方言由官方的 `rmcp` SDK 提供服務, 外層套著服務迴圈自身的行長度上限與解析閘門 (信任面的決策見 [rationale.md](./rationale.md#mcp-伺服器行為))。
- **信任方向**: 用戶端程式 (harness) 只有在被*准入*之後才受信任。此邊界同時承載協定正確性與授權: 一旦存在受信任用戶端允許清單, 准入就在這裡決定。
- **強制執行 (准入)**: 在服務任何工具呼叫之前, 伺服器先以 `attest_parent()` 證明產生它的用戶端程式, 再把該身分與信任記錄 (`runtime_dir()/trust.json`, 由 `pair-client` / `revoke-client` / `list-clients` 管理) 中已配對的用戶端比對。准入以經證明的錨點 (程式碼簽署者或映像雜湊) 為鍵, 絕不使用用戶端自稱的名稱。
- **`attest_parent()` 量測什麼**: Unix: `getppid()` 所指父程序正在執行的映像 (macOS: 經驗證的 `cdhash` 加簽署 Team ID; Linux: `/proc/<pid>/exe` 的 SHA256)。Windows: 建立伺服器 stdin 管道的那個程序 (映像 SHA256 加 Authenticode 發行者作為簽署者), 因為記錄下來的父程序在 `CreateProcess` 時可由呼叫者任意指定; 管道兩端必須指向伺服器以外的同一個程序, 否則失敗即關閉。
- **准入態勢**: 未登記 (尚未配對任何用戶端) 時維持原有的開放態勢, 並以 ERROR 等級記錄日誌; 一旦配對了用戶端, 任何不匹配者都失敗即關閉, 包括無法量測的身分與無法讀取的記錄。
- **殘餘風險**: stdin 是匿名管道, 沒有核心層的對端憑證, 所以被證明的一方是*產生*伺服器的程序, 而非寫入其 stdin 的程序。之後的重新認父 (Unix) 會讓准入失敗即關閉, 但管道 fd 可被繼承, 意味著產生者與 stdin 寫入者無法被證明是同一個; 這不是對管道的核心證明。此殘餘風險的 Windows 形式見[威脅模型](threat-model.md#殘餘風險-已接受已追蹤)。
- **強制執行 (撤銷)**: 准入不是一次決定就算數。位於 `runtime_dir()/trust.json` 的信任記錄會在工作階段內每個請求之前重新讀取 (由中介 (broker) 執行的逐請求准入閘門), 閒置連線則由計時器定期重讀 (監看器), 因此從任一介面執行的 `revoke-client` 都會讓被撤銷用戶端程式的下一個請求以失敗即關閉的方式被拒絕, 其重新接入也會被拒絕。這些路徑上的每次讀取都失敗即關閉。刪除該記錄則是[威脅模型](threat-model.md#重建帶來的變化-新的信任邊界)所點名的殘餘風險。
- **強制執行 (緊急開關)**: 同一份記錄也承載全域的緊急開關 (kill switch) 閂鎖, 與其紀元遞增一起原子性寫入。只要閂鎖設定中 (或記錄無法讀取), 來自每個用戶端程式的每個 `tools/call` -- 中介自己的以及每個中繼的, 它們共用同一個分派器 -- 都會在任何路由之前以穩定的 `BRIDGE_KILLED` 分類碼回應。用戶端程式的連線刻意保持開啟, 讓拒絕以型別化錯誤送達, 而非不透明的斷線。解除是明確的動作 (`unkill` - 絕不由擴充功能解除, 其解除路徑已經退役: 主機會拒絕由擴充功能發起的 `kill_release` 並稽核該次嘗試), 需要一次使用者在場證明 (在已登記的 Mac 上是一次 Secure Enclave Touch ID 觸碰; 沒有 Enclave 金鑰時則是 CLI 在終端機中輸入的確認, 且直接拒絕以管道導入的 stdin), 並在記錄無法讀取時拒絕。兩種轉換都會被稽核; 解除記錄會帶上授權它的認證路徑。
- **強制執行 (協定)**: 嚴格的 JSON-RPC 解析; 未知方法 -> `-32601`; 解析錯誤會回報, 而非致命; **stdout 只承載協定** (診斷輸出走 stderr, 否則一次誤寫就會破壞串流)。

## 邊界 2: Rust MCP 伺服器 <-> 原生訊息主機 (橋接 socket, NDJSON)

- **信任方向**: 這是唯一一道針對*本機*對端設防的邊界 - 任何可能嘗試連上橋接器的程序。
- **所有權**: 此邊界的伺服器端是**中介**: 第一個繫結 socket 與鎖定檔的 MCP 伺服器實例。之後經證明的實例透過同一個 socket 以中繼身分接入, 中介把它們各自用戶端程式的工具呼叫多工到同一個共用工作階段; 瀏覽器的原生訊息主機也一併接入。HMAC 交握完成後, 每個對端都必須立即送出一個宣告角色的接入訊框 (`AttachRequest`: 瀏覽器或中繼用戶端), 以失敗即關閉的方式讀取; 中繼的接入訊框還額外帶上其經證明的用戶端程式身分, 供邊界 1 的允許清單決策使用。中介以用戶端程式數量做參考計數, 最後一個離開時就結束; 舊的「最新者勝出」接管機制 (對前任擁有者送 SIGTERM) 已經移除。
- **強制執行**:
  - **沒有監聽埠**: 在 Unix 上, 橋接器是位於 0700 使用者專屬目錄內的 **0600 Unix domain socket**, 所以沒有任何 localhost 埠可供其他程序連接, 而檔案系統權限把其他使用者擋在外面。在 Windows 上它是一個具名管道, 其安全描述元只准許目前使用者, 由核心在開啟時把其他使用者擋在外面。
  - **對端 UID 檢查** (Unix): 在 `accept` 時, 伺服器從核心讀取連入對端的 UID (`getpeereid` / `SO_PEERCRED`), 在認證之前就丟棄任何不是來自自身 UID 的連線。在 Windows 上, 管道的描述元就是這道檢查, 由核心在連線存在之前強制執行。
  - **由核心證明的執行檔身分**: 仍在認證之前, 每一端都為對端取得一個由核心證明的身分, 並要求它與自己正在執行的映像相符, 所以同一使用者的其他程式會在這裡被拒絕。證明是**雙向的**: 伺服器在 `accept` 後證明主機, 主機在 `connect` 後證明伺服器。
  - **Linux 身分**: 來自 `SO_PEERCRED` 的對端 PID, 接著是 `/proc/<pid>/exe` 的 SHA256 (綁定到正在執行的 inode, 解析時存在一個狹窄的 pid 重用競態)。
  - **macOS 身分**: 對端的核心**稽核權杖** (`LOCAL_PEERTOKEN`), 以 `SecCodeCheckValidity` 驗證並按 `cdhash` 比對, 綁定到正在執行的映像, 同時關閉路徑重新開啟的 TOCTOU 與 pid 重用競態。只有當核心回報不支援稽核權杖選項時 (`ENOPROTOOPT`, 較舊的系統), 才回退到以 pid 識別的 `SecCode`, 此時狹窄的 pid 重用競態仍然存在; 任何其他錯誤都失敗即關閉。
  - **Windows 身分**: 核心為管道另一端記錄的 pid, 接著是該 pid 所執行映像檔的 SHA256, 透過路徑重新開啟取得; [威脅模型](threat-model.md#殘餘風險-已接受已追蹤)記錄了這留下的缺口。
  - **HMAC 挑戰回應**: 伺服器送出一個新鮮的隨機 nonce; 主機以 `HMAC-SHA256(secret, nonce)` 回覆, 並以常數時間驗證。每次執行的秘密 (0600 鎖定檔) 從不經過線路傳輸, 而每條連線各自的 nonce 可抵擋重放。
  - 每條連線都是經過大小檢查的 NDJSON; 同一標籤下的瀏覽器重新連線會取代該標籤先前的寫入者。中介也對這個介面設限: 最多 16 個不同的瀏覽器標籤與 8 個用戶端程式, 最多 32 條處於交握中的連線, 交握加接入的讀取逾時為 10 秒, 以及每個中繼各自的速率限制。
  - **緊急開關**: 閂鎖設定期間, 中介的監看器會在其一秒一次的滴答內切斷每條活躍的瀏覽器連線 (把進行中的呼叫排空為型別化失敗), 瀏覽器接入則在准入時被拒絕。無法讀取的信任記錄得到同樣的處置: 緊急開關狀態不可知時, 不允許任何瀏覽器連線存在。中繼保持接入; 它們的呼叫在邊界 1 以型別化方式被拒絕。
  - **Windows 殘餘風險**: 映像是透過重新開啟其路徑來量測的, 而持有秘密的鎖定檔在那裡沒有設定明確的權限模式, 而是依賴使用者專屬執行階段目錄的預設權限 (`LOCALAPPDATA`, 或 `USERPROFILE\AppData\Local`; 最後手段的暫存目錄不保證是使用者專屬的; 見 `src/packages/core/src/ipc/` 中的 `runtime_dir()`)。[威脅模型的殘餘風險](threat-model.md#殘餘風險-已接受已追蹤)承載前者; 秘密只是四道閘門之一, 不是唯一一道。
  - **殘餘風險**: 雜湊與程式碼簽章都無法區分由瀏覽器正當產生的主機, 與被同一使用者的攻擊者重新執行的同一個執行檔: 位元組與 cdhash 完全相同。要補上這點需要瀏覽器/擴充功能端的配對 (在擴充功能設定中首次使用即信任)。在 macOS 上, 信任固定到一個精確的 cdhash; Team ID / 指定需求 (designated requirement) 固定 (以同時接受另一個受信任的建置) 是延後的後續工作, 不是同一執行檔橋接中的缺口。

## 邊界 3: Chrome <-> 原生訊息主機 (Native Messaging 訊框格式)

- **信任方向**: Chrome 依主機資訊清單產生主機, 清單中的 `allowed_origins` **固定了擴充功能 ID** - 只有我們的擴充功能能與之對話。
- **強制執行**: 4 位元組小端序長度前綴加 JSON; 入站 64 MB 上限, 出站 1 MB 上限; stdout 單一寫入者加逐訊框 flush; `panic = "abort"` 加 stderr panic hook, 讓 panic 無法破壞訊框串流。stdin EOF 時關閉。
- **主機處理的控制訊框**: 登記儀式、用戶端管理交換、緊急開關訊框 (`kill_status`/`kill_engage`/`kill_release` -> `kill_status_result`), 以及射後不理的 `audit_event`, 都由主機本身回應, 絕不轉送到 MCP 伺服器; 同樣的訊框類型若從伺服器那一側到達, 則視為注入而丟棄。`audit_event` 還額外受種類允許清單約束 (只允許擴充功能所擁有的確認/登記種類), 而且由主機自行蓋上介面標記, 所以瀏覽器那一側無法把主機側事件偽造進稽核日誌。`kill_release` 是唯一會恢復能力而非削減能力的管理訊框, 主機會直接拒絕並稽核: 解除是 app/CLI 在在場閘門之後的動作, 擴充功能只保留啟用 (煞車在每個介面上都只需一個動作, 恢復能力則否)。緊急開關閂鎖設定期間, 主機以純控制平面模式執行: 從不撥接中介, 丟棄橋接訊框, 並恰好讓這些控制訊框維持運作, 使狀態、啟用與策略拉取在已切斷時仍可觸及。
- **殘餘風險 (主機到擴充功能未經認證)**: `allowed_origins` 固定了哪個擴充功能可以開啟主機, 但沒有任何東西固定擴充功能會接受哪個主機。資訊清單位於使用者可寫入的目錄, 所以同一使用者的攻擊者可以把它的 `path` 改指向惡意的主機執行檔。瀏覽器啟動那個執行檔, 它直接以 native messaging 與擴充功能對話, 繞過邊界 2 的已認證 socket。補上這點需要在擴充功能中實作首次使用即信任的主機身分配對。見[威脅模型](threat-model.md)。

## 邊界 4: 擴充功能 <-> 網頁 (Chrome API / 內容指令碼 / DOM)

- **信任方向**: **頁面不受信任。**這是安全上最關鍵的邊界。
- **強制執行**:
  - **允許清單**: 頁面層級的操作只在使用者核准的來源 (origin) 上執行; 新的來源會提示使用者並請求主機權限。頁面無法自行核准。
  - **確認**: 送出/連結點擊、`page_press`、`page_select`、`page_eval`、關閉分頁與 `page_upload` 都在擴充功能擁有的彈出視窗 (`confirm.html`) 上確認, 那是一份 `chrome-extension://` 文件, 在自己的程序中執行, 頁面無法讀取、覆蓋或自動點擊; 路由器只接受來自那份確切文件的 ready/resolve 訊息。逾時、關閉與缺少提供者都視為拒絕。只有這些高風險操作需要確認; 低風險操作 (導覽、`page_text`、`tab_list`、經遮罩的 cookie 或儲存空間讀取) 執行時沒有逐動作提示。與開啟中的確認競爭的導覽, 由一個在頁面中與動作原子性執行的來源斷言攔截; 點擊還額外綁定到已核准的目標描述元。在已登記的 Mac 上, `page_eval`/`page_upload` 的核准經由主機的 Secure Enclave (Touch ID) 進行。
  - **遮罩**: 頁面文字、cookie、儲存空間與 eval 輸出在 Service Worker 中 (`egress.ts`) 於回傳給模型之前就被遮罩, 兩個頁面後端共用這一次遮罩。
  - **信任狀態隔離 (#32)**: `storage.local` 與 `.session` 透過 `setAccessLevel(TRUSTED_CONTEXTS)` 限定在擴充功能情境內, 所以內容指令碼無法讀寫登記固定值、已遭入侵標記、已強制執行的策略狀態 (策略棘輪與切換旗標) 或允許清單。在該限制生效之前, 登記閘門失敗即關閉。殘餘風險: 非同步限制解析完成之前, 有一個次毫秒級的冷啟動視窗 (見威脅模型)。
  - **緊急開關鏡像與稽核環**: 主機緊急開關狀態的 SW 專屬鏡像與擴充功能的稽核環, 都存放在同一個受限儲存空間中。鏡像讀到已切斷、未知或格式錯誤時, 請求閘門一律拒絕 (垃圾資料絕不會對應到寬鬆的「不存在」狀態); 鏡像只從主機的 `kill_status_result` 訊框寫入, 絕不從執行階段訊息寫入。路由器只接受來自擴充功能自身頁面的 `get_kill`/`set_kill`/`get_audit`, 所以沒有任何頁面或內容指令碼能讀取狀態、切換開關或讀取稽核日誌。
  - **隔離**: 內容指令碼在隔離世界中執行; `page_eval` 使用 `Function` 建構函式 (而非內容指令碼的作用域), 其結果在遮罩前會被安全地序列化 (循環參照/DOM/特殊型別)。兩個頁面後端執行同一份共用、自足的 DOM 實作 (`lib/dom/page-api.ts`); CDP 路徑傳送的是其字串化的原始碼, 所以兩者不可能分歧。
  - **唯讀憑證**: 不寫入 cookie/儲存空間。

## 不得倒退的不變量

- 兩種執行檔模式下的 stdout = 只有協定位元組。
- 橋接器絕不服務任何未通過以下檢查的連線: 同一使用者檢查 (Unix 上的對端 UID, Windows 上的管道描述元)、執行檔身分證明、HMAC 交握, 或必要的宣告角色接入訊框。
- 一旦受信任用戶端允許清單存在 (已登記), 任何用戶端程式除非其經證明的身分與允許清單錨點相符, 否則不予服務 -- 無法量測的身分與無法讀取的允許清單都失敗即關閉, 而用戶端自稱的名稱絕不是授權的鍵。
- 主機資訊清單的 `allowed_origins` 永遠恰好固定我們的擴充功能 ID。(這只固定了擴充功能到主機的方向; 主機到擴充功能的跳點尚未經過認證。見邊界 3。)
- 沒有任何頁面層級工具會在未列入允許清單的來源上執行 (除非設定了 `allowAllSites`)。
- 沒有任何工具會寫入 cookie 或網頁儲存空間。
- 緊急開關啟用期間, 或其記錄無法讀取時, 不服務任何工具呼叫, 也不允許任何瀏覽器連線存在; 開關只能由受信任介面的明確解除動作清除, 絕不會自動清除。
- 稽核日誌從不作為決策的閘門: 記錄採「先決定後記錄」, 寫入失敗時丟棄該筆記錄 (透過丟棄計數器可見), 而不會讓操作在任一方向上失敗。

變更以上任何一條都是**安全相關變更** (見 [SECURITY.md](../../../.github/SECURITY.md))。
