# 威胁模型

chromium-bridge 保护什么、防范谁, 以及它明确不防御什么。本页与 [trust-boundaries.md](trust-boundaries.md) 和[工具风险矩阵](tool-risk-matrix.md)配套阅读。

请先阅读[安全标准线](security-bar.md): 它说明这些机制承诺了什么, 而本页负责说明每一项是如何执行的。

## 资产

- 用户**已认证的浏览器会话** (Cookie, 包括 httpOnly Cookie, 以及 Web 存储中的令牌) - 也就是在用户已登录的站点上*以用户身份*行动的能力。
- 用户能看到的**页面内容**。
- 以用户身份**执行操作** (点击/填写/导航/eval) 的能力。
- **线路协议**的完整性 (一条损坏的流可以让桥挂起或崩溃)。

## 参与者

| 参与者 | 是否受信任? | 说明 |
|-------|----------|-------|
| 用户 | 是 | 拥有这台机器和 Chrome 配置文件 |
| MCP 客户端 (Claude Code、Codex 等) | **是, 这是设计使然** | 由用户配置; 由它驱动工具 |
| Rust 二进制 (MCP 服务器 + 原生消息主机) | 是 | 我们要保护的对象 |
| MV3 扩展 | 是 | 但与不受信任的页面代码并肩运行 |
| **网页** | **否** | 可能被攻击者控制; 可能承载提示注入 |
| 其他本地用户 / 进程 | **否** | 可能尝试连接桥接套接字 |
| 网络 | 不在范围内 | 没有远程攻击面 - 一切都在 localhost/stdio 上 |

## 信任假设

- **单用户机器。** 桥是一个位于 0700 每用户目录中的 0600 Unix 域套接字 (没有监听端口), 由内核对端 UID 检查、由内核证明的可执行文件身份, 以及基于每次运行密钥的 HMAC 挑战-应答共同把关; 模型假设不存在拥有相同 UID 的敌意本地用户。证明还能拒绝*另一个*同用户二进制, 但无法阻止重新运行*我们自己的*二进制的同用户攻击者 (见威胁 #4)。
- **MCP 客户端是受信任的。** 用户自己安装的恶意客户端不在范围内 - 它已经拥有用户授予它的一切。这些工具存在的目的就是被该客户端驱动。
- **Chrome 的沙箱和扩展模型成立。** 我们依赖 MV3 在内容脚本与页面 JS 之间的隔离, 以及 Chrome 对主机权限的强制执行。

## 主要威胁与缓解措施

1. **网页诱导代理在未经批准的情况下对其进行操作。** -> 页面级操作要求**已列入站点白名单的源 (origin)**; 新的源会触发明确的用户提示 + `chrome.permissions.request`。页面无法把自己加入白名单。

2. **提示注入: 页面内容诱骗模型发起危险的工具调用** (例如「运行这个 eval」、「读取 Cookie 并把它们发出去」)。 -> 对代理而言, 观察到的页面内容是*数据*, 不是命令。独立于此, 高风险操作 (提交/链接点击、`page_eval`、关闭标签页) 要求**在扩展自有窗口中进行用户确认**, 页面无法伪造、读取或自动关闭该窗口; `page_eval` 则**每次调用**都要确认, 并显示完整代码。这种逐操作提示只覆盖高风险操作。低风险操作 (导航、`page_text`、`tab_list`, 以及脱敏后的 Cookie 或存储读取) 不带逐操作提示, 因此一个已经能触达扩展的驱动者可以导航、读取脱敏后的页面内容、枚举标签页, 而用户看不到其中每一步。确认是针对危险操作的门禁, 不是「不会有任何事情悄悄发生」的承诺。这些门禁默认开启; 每一项都是有文档记录的设置, 其选择退出后的残余风险列表见 [SECURITY.md](../../../.github/SECURITY.md#page_eval-and-confirmation-defaults-fail-safe)。

3. **凭据/令牌外泄。** -> Cookie/存储是**只读的** (没有 set), **限定在白名单范围内**, 并在离开扩展之前经过**脱敏** (JWT/十六进制/长数字串/类令牌形状)。`storage_get` 的脱敏不可由用户关闭。`page_text` 会对密码和类似银行卡号的数字脱敏。

4. **另一个本地进程劫持桥**, 用来发起工具调用或读取响应。 -> 每条连接都要通过同用户检查、由内核证明的可执行文件身份, 以及一次 **HMAC-SHA256 挑战-应答**, 其中每次运行的密钥从不经过线路, 新鲜的 nonce 挫败重放。证明是双向的 (主机与服务器互相证明)。

   在 Unix 上**没有监听端口**: 桥是 0700 目录中的 0600 Unix 域套接字, **内核对端 UID 检查**拒绝其他用户。对端的身份必须与我们一致: 在 Linux 上是其 `/proc/<pid>/exe` 的 SHA256, 在 macOS 上是其运行中映像的 `cdhash`, 通过内核审计令牌经 Security 框架识别, 因此*另一个*同用户程序在能够认证之前就被拒绝。

   在 Windows 上, 桥是一个命名管道, 其安全描述符只允许当前用户 (内核在打开时强制执行), 两端互相证明对方的映像: 内核为管道对端记录的 pid、它所运行映像文件的 SHA-256, 以及对客户端程序 (harness) 而言它的 Authenticode 发布者。按路径度量是下文的一项残余风险。

   锁文件在 Windows 上没有显式设置模式, 依赖每用户运行时目录的默认权限 (`LOCALAPPDATA`, 或 `USERPROFILE\AppData\Local`; 作为最后手段的临时目录不保证是每用户的; 见 `src/packages/core/src/ipc/` 中的 `runtime_dir()`)。

   **未覆盖:** 重新执行*我们自己的*二进制的同用户攻击者与合法主机逐字节相同 (相同的哈希, 相同的 cdhash), 因此哈希和代码签名都无法区分它们。登记仪式 (威胁 #6) 使扩展与桥的*配对*受在场门禁保护, 但在登记之后不区分同用户进程 (见清单替换残余风险)。macOS 上的 Team-ID 固定 (同时信任另一份单独签名的构建) 已推迟。

5. **畸形/超大消息使桥崩溃或损坏。** -> Native Messaging 帧格式经过长度检查 (入站 64 MB 钳制上限, 出站 1 MB 上限); `panic = "abort"` 配置 + stderr panic 钩子让 panic 远离协议流; 解析错误被上报, 而非致命; cargo-fuzz 目标 (`src/packages/core/fuzz/`) 既覆盖线路解析器 (Native Messaging 帧格式、MCP JSON-RPC、桥接与握手解码器), 也覆盖其背后的语义校验器 (握手 MAC 校验器、帧分类器、DER 签名解析器、Enclave 挑战构造器, 以及清单归属判定)。

6. **静默配对: 恶意的 `claude mcp add` (或任何能写入 MCP 客户端配置的进程) 在用户毫无察觉的情况下搭起整条链路。** -> **登记仪式** (在 macOS 上默认开启): `chromium-bridge pair` 在 Secure Enclave 内铸造一把 P-256 密钥, 该密钥的每次使用都要求用户在场 (Touch ID / 密码), 并执行一次受在场门禁保护的自测签名; 拒绝它则机器保持未登记状态。扩展固定该公钥, 并据此验证 `enclave_proof` 帧; 在未登记的机器上, 挑战会得到 `enclave_error: not_enrolled`, 已固定的扩展会失败即关闭。重新固定 (`pair --reset`) 再次要求在场, `revoke` 则删除密钥, 使任何证明都无法产生。用户把 `pair` 打印的 SHA-256 指纹与扩展显示的指纹比对, 这能挫败位于两者之间的中间人主机。**范围:** 这关闭了静默*首次*配对和静默重新固定; 它**不**关闭登记后的同用户替换 (见下文残余风险)。

7. **已吊销的客户端或已吊销的主机继续行动, 因为吊销没有到达执行点。** -> **任一侧吊销纪元**: 信任记录 `runtime_dir()/trust.json` 中的一个计数器, 每个执行点都重新读取整条记录。客户端吊销和紧急开关 (kill switch) 的状态切换都落在递增该计数器的那一次 `trust.json` 写入中; 主机密钥吊销则是一次钥匙串删除, 加上同一运行时锁下的一次单独的尽力而为纪元递增, 递增失败会在下一次密钥验证时暴露。`revoke-client` (来自 CLI, 或来自扩展经主机中介的 `client_revoke` 帧) 重写白名单并递增纪元; 存活的中介 (broker) 的逐请求准入门禁及其空闲连接监视器随即以失败即关闭的方式丢弃被吊销的客户端程序, 并拒绝其重新接入。主机密钥的 `revoke` / `pair --reset` 删除 Enclave 密钥并递增纪元; 原生消息主机确认钥匙串中的密钥已不存在, 并推送一个由主机发起的 `enclave_revoked` 帧, 因此已固定的扩展无需等待可选的重新验证即失败即关闭。现在从任一侧解除配对都会删除凭据的两半 (扩展侧的吊销也会要求主机删除其密钥, 并持久化地重发直到被确认)。纪元是变更通知, 从来不是权威: 篡改它的同用户写入者可以强制一次多余的推送, 或让每次读取都失败即关闭, 但无法让配对列表或钥匙串中不存在的任何人获得准入。**范围:** 套接字这一段是即时的; 扩展对主机密钥吊销的反映受限于下一次 Service Worker 唤醒。已被攻陷但仍在白名单中的客户端在被吊销之前保持受信任 (证明识别的是二进制, 不是意图)。被替换的原生消息主机 (威胁 #4 的清单替换残余风险) 可以伪造 `enclave_revoked` 推送, 使已固定的桥失败即关闭, 这是针对用户自己的桥的拒绝服务, 不授予任何能力, 也无法在用户空间中通过认证消除。

## 明确的非目标

- 防御被攻陷的操作系统账户, 或运行*我们自己的*二进制的同用户攻击者。对端 UID 检查和可执行文件证明拒绝其他用户和其他二进制, 但执行正版二进制的同用户进程与合法主机逐字节相同, 对 IPC 层而言仍在范围之外 (见威胁 #4)。
- 防御用户自己配置的恶意 MCP 客户端。
- 多用户 / 共享机器隔离。
- 远程攻击者 (不存在远程攻击面)。

## 残余风险 (已接受、已跟踪)

- **Native Messaging 清单替换 (主机到扩展这一跳未经认证)。** 桥用对端 UID 检查、证明和 HMAC 认证主机到服务器的套接字这一跳, 但没有任何东西向扩展认证原生消息主机。主机清单位于用户可写的目录中, 因此同用户攻击者可以改写其 `path`, 把浏览器指向恶意的主机二进制。浏览器随后启动该二进制, 它直接与真正的扩展讲 Native Messaging, 发出 `BridgeReq` 而从不触碰经过认证的套接字。`allowed_origins` 固定了哪个扩展可以打开主机, 但没有任何东西固定扩展会接受哪个主机。登记仪式收窄了这一点: 有了扩展侧的固定, 被替换的主机无法在不弹出用户意料之外的 Touch ID 提示的情况下出示有效的 `enclave_proof`, 因此*登记时*的替换不再是静默的。仍然敞开的是在场检查*之间*的替换: MV3 在每次 Service Worker 重启时 (大约每空闲五分钟一次) 重新生成主机进程, 在场无法按每次重连要求 (每五分钟一次 Touch ID 提示是不可能发布的), 而任何静默的逐重连凭据都可以被任何同用户进程使用。因此在登记之后, 换掉清单或重新执行我们二进制的同用户攻击者在重连时无法区分。可选的逐操作在场层级 (单独跟踪) 是能够关闭这一剩余部分的机制。
- **已批准源上的读取外泄 (已接受)。** 一旦某个源进入白名单, 读取按设计不再提示: `page_text`、`cookie_get` 和 `storage_get` 运行时没有逐操作确认, 只受启发式脱敏保护。因此, 在已批准且已登录的源上成功对模型实施提示注入的页面, 可以静默读取页面内容, 以及脱敏启发式漏掉的任何秘密 (它们匹配的是类令牌的形状而非含义, 所以新颖的格式可能漏过)。把读取放到逐操作提示之后曾被考虑并否决: 那会给几乎每一步代理操作都加上确认, 教会用户机械点过那些守护真正危险操作的提示。这是一项有意识接受的残余风险; 缓解措施是源白名单 (页面必须已经处于用户批准过的地方)、作为尽力而为层的脱敏, 以及审计日志。
- **高风险点击宽限期**允许*无关的*同源代码在不重新提示的情况下运行: 一次提交或链接点击被批准后, 同一源和同一操作类型在 60 秒内跳过确认。`page_eval` 不在此宽限期内; 它每次调用都重新确认。
- **信任状态隔离存在冷启动窗口 (#32)。** 登记固定、已攻陷标记、已执行的策略状态 (策略棘轮和切换标志) 以及白名单都存放在 `storage.local` 中, 而 Chrome 默认把它暴露给内容脚本。扩展用 `setAccessLevel(TRUSTED_CONTEXTS)` 把两个存储区都限定在扩展上下文内, 并在此生效之前让登记门禁失败即关闭。运行时消息路由器 (通往同一状态的中介路径) 拒绝所有发送者不是扩展自身页面的消息, 因此内容脚本无法通过 `add_allow` 植入白名单, 也无法通过 `get_enrollment` 读取已固定的密钥 id/指纹。由于 `setAccessLevel` 是异步的, 且在 Service Worker 启动之后才应用, 冷启动时仍留有一个亚毫秒级的窗口, 其中来自上一个 worker 生命周期、处于被攻陷渲染器中的内容脚本, 可以在限制生效之前直接向 `storage.local` 写入被篡改的值; 限制随后把它锁定下来。在路由器受门禁保护之后, 这个冷启动窗口是内容脚本通往信任状态的唯一剩余路径。没有用户空间 API 能关闭它; Enclave 仪式的密码学检查限定了, 但不能消除, 一个被植入的固定所能达成的效果。
- **高风险确认现在渲染在页面可触及的 DOM 之外。** 每一种高风险确认 (提交点击、`page_press`、`page_select`、`page_eval`、`tab_close`、`page_upload`) 都显示在专用的 `confirm.html` 弹出窗口中, 这是一个运行在自身进程中的 `chrome-extension://` 文档。受保护的页面无法读取、聚焦、覆盖或点击它, 消息路由器也只接受来自该确切文档的确认就绪/决议消息。这关闭了早先的残余风险: 当时提示条绘制在页面自己的 DOM 中 (或在 CDP 下绘制在其 MAIN world 中), 被提示注入的页面可以用 `MutationObserver` 盯着它并自己点击「允许」。在确认打开期间与流水线竞争的导航, 由在页面中与动作原子执行的源断言捕获, 点击还额外绑定到用户批准的目标描述符。残余: 该窗口证明的是在页面无法触及的表面上发生了一次点击, 不是密码学意义上的用户在场; Secure Enclave 在场门禁为两个最核心的工具关闭了这一剩余部分: 在已登记的 Mac 上, `page_eval`/`page_upload` 的批准经由主机 Secure Enclave 路由, 裁决是不可伪造的、由主机签名的用户在场检查 (Touch ID 或登录密码)。对于其他高风险类型、在非 macOS 平台上、在未登记的 Mac 上, 以及主机策略选择退出 `touchIdConfirm` 时 (这种放宽本身需要一次签名的、受在场门禁保护的策略写入: 在已登记的 Mac 上是 Touch ID, 在未登记的 Mac 上则被拒绝), 该窗口仍是确认表面。
- **`page_upload` 可以附加调用者指名的任何本地文件。** 当该工具启用时 (默认关闭), 它会把调用提供的任意绝对路径附加到文件输入上, 因此被诱导在某页面上调用它的模型可以把用户从未选择过的文件交给该页面, 例如 SSH 密钥或私人文档。它前面有三道门禁: 选择启用、源白名单, 以及显示确切路径的逐调用确认 (在已登记的 Mac 上是 Secure Enclave 用户在场检查; 其他情况下是页面无法触及的扩展窗口)。仍然敞开的是路径本身不受限于用户挑选的文件或安全目录: 一次被批准的调用附加的正是它所指名的文件。在推荐文件上传用于一般用途之前, 已跟踪待加固 (改用操作系统文件选择器, 让模型不指名任何路径)。
- `page_snapshot_precise` 会短暂附加调试器 (横幅闪现)。
- **Windows 按路径度量映像 (已接受、已跟踪)。** 管道对端的 pid 解析为映像路径, 哈希和签名从该文件读取, 而不是从已映射的映像读取, 因为用户态拿不到后者的句柄。Windows 允许正在运行的可执行文件被重命名, 因此同用户进程可以在启动与度量之间把另一个文件放到该路径上; Linux 所带的 pid 复用竞争同样适用。
- **Windows 上的客户端程序是服务器 stdin 管道的创建者。** 记录的父进程在 `CreateProcess` 时可由调用者选择, 因此服务器度量的是在其 stdin 管道两端都被记录的那个进程, 对其他任何情况 (控制台、来自两个进程的两端) 都失败即关闭。
- **持有客户端程序管道一端的进程可以在其上运行服务器 (Windows)。** 客户端程序以管道 stdin 生成的子进程通过继承持有该端, 可以启动一个证明该客户端程序的服务器; 匿名管道是单向的, 所以它只能读取客户端程序自己的请求。对客户端程序拥有 `PROCESS_DUP_HANDLE` 的同用户进程还可以复制写入端并注入请求: 这是[边界 1](trust-boundaries.md#边界-1-mcp-客户端---rust-mcp-服务器-stdio-json-rpc-20)的 stdin 写入者残余风险。
- **Windows 发布者锚点跳过吊销检查 (已接受、已跟踪)。** `WinVerifyTrust` 运行时不做吊销检查, 这与浏览器自身安装程序验证所用的策略相同: 在线检查会在离线时拖住启动, 仅缓存的检查则在从未获取过 CRL 的机器上失败。因此被吊销的发布者证书会保留其锚点, 直到 `revoke-client` 将其移除; 目录签名的映像没有嵌入式签名, 仅按哈希锚定。
- **CDP 模式** (`cdpMode`, 一项主机持有的策略授予, 默认关闭; 启用它是一次签名的、受在场门禁保护的策略写入 - 在已登记的 Mac 上是 Touch ID, 在未登记的 Mac 上则被拒绝) 把所有页面操作经由 `chrome.debugger` 路由。启用后它**绕过页面 CSP** (让 `page_eval` 能在严格 CSP 的站点上运行), 并对该标签页保持**持久的调试器附加** (「Started debugging this browser」横幅一直显示)。白名单、逐操作确认和脱敏保持不变; 残余风险在于更宽的攻击面和被移除的 CSP 纵深防御层, 作为选择启用的明确代价被接受。
- **注册修复不受在场门禁保护。** 选项页的 `registration_repair` 帧通过与 `doctor --fix` 相同的接缝重新注册检测到的浏览器: 幂等, 且只把浏览器指向这个二进制而非其他任何东西, 与 CLI 路径的姿态相同, 后者同样没有门禁。被攻陷的扩展所能获得的, 不过是任何同用户进程本就拥有的 (威胁 #4 的类别)。

### 主机持有策略的残余风险台账

主机持有策略的工作把安全策略移到了主机侧: 一份签名的基线、一个未签名的限制覆盖层、扩展侧的取值棘轮, 以及逐连接的分发屏障。实现评审点名了下列残余风险, 每一项都是有意接受的; 各条目说明可能发生什么、确切的前提条件、什么限定了它, 以及为什么接受。[SECURITY.md](../../../.github/SECURITY.md) 指向这里, 承重的代码注释也一样。请把这些条目放在一起读, 而不是孤立地读 - 它们会叠加。一个实例: 第一条的界限 (只接受存储修订号及以上的正版基线) 锚定在存储的棘轮记录上, 而下文的冷启动条目使该记录在其窗口内可被删除 - 锚点一旦被删除, 该密钥曾签过的最宽松的正版基线就会作为首次策略应用, 修订号不限。

- **一次失败的攻陷标记持久化加上一次 worker 重启, 会让屏障对捕获到的正版策略重新打开。** 当一次策略推送针对固定的签名验证失败时, 扩展会同步锁存一个内存中的攻陷标志, 然后写入持久的攻陷标记。如果这次持久写入失败, 随后 Service Worker 重启, 新的 worker 将在未锁存、无持久标记的状态下启动, 于是重放的正版、逐字节相同的 `policy_current` 能通过验证, 作为幂等重放推进棘轮, 并重新打开分发屏障。前提条件: 一次持久存储写入失败 (边缘情况)、一次 SW 重启, 以及一个被捕获的正版帧。界限: 屏障只会对已固定密钥在存储修订号及以上签过的某份正版策略重新打开 - 攻击者在其捕获的文档中挑选, 但无法伪造一次越过棘轮和签名触及集规则的新放宽 - 而主机重新证明只在用户选择启用周期性重新验证的地方进一步收窄它 (`hostReverifyMs`; 默认值 0 下没有任何重连会被质询, 因此界限只靠棘轮本身支撑)。在一个 worker 生命周期内, 内存锁存无论如何都成立。失败的持久化会被记录, 从不被静默吞掉 - 但在这一前提下, 没有任何关于它的持久证据能幸存: 审计事件写入的是刚刚失败的同一存储, 而这种攻陷类型是扩展本地的, 从不转发到主机的审计日志。接受的原因是内存锁存按定义无法在重启后幸存; 彻底关闭它需要「持久写入成功后再继续」或启动时重新证明, 而不是更宽的锁存。
- **同密钥撤销路径中的一个微任务窗口。** 恢复被取代的已存储策略记录的写入撤销, 会在其恢复性写入之前立即重新检查固定重置纪元, 但 `chrome.storage` 不是事务性的, 所以在那次最终检查与写入之间完成的同密钥重新配对, 仍可能看到撤销恢复了重置刚刚移除的记录。按构造是单向的: 纪元在读取先前记录之前捕获, 所以另一侧的误触发会把恢复变成移除 (失败即关闭), 而幸存的方向只能复活一条惰性记录, 作用域检查会让它在任何其他固定下都不进入执行。接受: 没有事务性存储就无法修复。
- **一次推送内的分歧, 以及与错误推送的验证竞争的请求。** 两个执行点 (主机分发、扩展门禁) 在策略变更前后可能短暂不一致; 窗口为一次推送, 且扩展在其边界上是权威 (主机持有策略的一个已命名后果)。另外, 策略帧在请求门禁之前路由, 但不与请求队列排序 (紧急开关帧接受过的同一种空路由): 帧路径与请求路径不共享计数器, 所以在错误签名的推送到达与其签名验证实际失败之间 (隔着一次帧链跳转、两次解析、一次 base64 解码、一次固定读取和一次 ECDSA 验证), 已经通过门禁的请求 - 复数, 没有什么把它们限定为一个 - 仍可以在仍然打开的屏障下分发。限定它的是: 生命周期内的攻陷锁存在验证失败的那一刻同步置位, 且每个请求读取它两次 (在门禁处折叠, 并在分发自身的策略读取中再读一次), 所以请求必须在失败落地之前通过两次读取; 而漏过的请求是在存储的有效策略下运行的, 即经棘轮推进的下限, 它从不比用户上次看到的已应用策略更宽松。
- **抛出异常的在场探测会拒绝该操作 - 刻意不回退到窗口。** 如果询问「硬件在场路由是否可用」的探测抛出异常 (这是异常情况: 被攻陷或缺失的固定会干净地返回 `false`, 不抛异常), 操作将被拒绝。旧行为会回退到扩展窗口确认; 恢复这一回退会让任何探测故障把要求硬件 (`touchIdConfirm`) 的 `page_eval`/`page_upload` 批准降级为普通的窗口点击 - 这是在场阶梯的不降级规则的反转。范围, 精确表述: 这只覆盖异常 (抛出) 路径。干净地报告没有硬件能力的探测仍然路由到窗口确认, 那是该状态下有文档记录的降级表面, 不是一次降级。代价是异常路径上的可用性, 从不是能力。
- **敌意的未固定主机可以用放宽提示占满确认 FIFO。** 在没有固定的机器上, 策略放宽会被搁置等待用户的窗口批准。对已在等待批准的推送的逐字节相同重放 (相同的基线字节、相同的覆盖层、相同的连接) 会折叠到待处理的提示上, 但候选内容不同的推送会各自串行化为一个提示, 所以敌意主机可以让全局确认 FIFO 一直忙碌, 只要用户一直不作答 - 而 FIFO 是跨所有确认类型全局共享的, 所以这种占用也会饿死排在它后面的 `page_eval`/`page_upload`/点击确认。两点细化, 点名如下: 折叠以 JSON 字符串化后的覆盖层为键, 所以键顺序被调换或做了细微变化的限制会使其失效 (代价是多一个提示, 从不抑制一次不同的推送); 以及伪造的未签名限制会静默应用, 完全没有提示 - 这是策略设计让步的伪造限制拒绝服务, 因为它只会移除能力。界限: 一次只有一个提示, 每次拒绝都被审计, 没有明确批准什么都不会放宽, 且已固定的机器不受影响 (那里不存在批准窗口)。一处溢出, 点名如下: 语言通道共享同一条帧通道, 所以在未固定的机器上, 一个排队的 120 秒批准提示可能延迟 `lang_choose` 的响应 - 无害, 因为本地的 `uiLanguage` 写入已经落地, UI 也已在中继之前完成切换; 只有诊断用的 `sent` 标志被延迟, 而且 `chooseLanguage` 在未固定的机器上本来就返回 false。接受: 未固定的批准窗口本质上可被唯一获准请求它的对端占用。
- **明确选择「en」会在每次重连时重新提供首次配对的语言采用。** 主机的语言存储把缺失的记录映射为默认值 (`"en"`, seq 0), 而携带已存储值的 `lang_set` 是刻意的空操作, 不递增任何东西 (语言通道的回声抑制规则) - 所以针对从未设置过的存储, 一次值为 `"en"` 的明确 `lang_set` 会让 seq 停在 0, 主机无法区分「从未设置」与「明确设置为默认值」。因此, 用户明确选择了英语的扩展在每次重连时都看到 seq 0, 并每次都重新发送它那一个采用性 `lang_set`, 永远如此。界限: 每次连接一帧 (逐连接的采用锁存在一次连接内结束它), 该帧在主机侧是空操作, 且该通道纯粹是装饰性的 - 语言是浏览器拥有的显示状态, 从来不是策略, 从来不是能力。按原样接受, 不是缺陷: 把「明确设置为默认值」折叠成一次 seq 递增, 会波及 seq 存在的目的所在的回声抑制语义, 为了装饰性收益冒真正的风险。
- **密钥销毁的纪元递增是尽力而为的。** `revoke` 和 `pair --reset` 在销毁临界区内清除签名的基线并递增主机密钥纪元, 但纪元写入本身可能失败, 于是在销毁过程中签名的首次写入基线可能随后落地。界限: 让它落地仍然需要一次真正的 Touch ID 触碰 (它是一次用户在场的签名写入), 且下一次登记在铸造密钥前无条件清除基线, 试图在新密钥存在并与之混淆之前将其移除 (该清除本身也是尽力而为的: 失败会告警, 铸造照常进行)。
- **损坏的攻陷标记读作未攻陷。** 持久攻陷标记的读取器对无法解析的记录返回 null, 所以损坏的标记读作「没有证据」- 这是模块级的, 波及继承它的八处以上读取点, 包括登记门禁、在场能力探测和配对通知抑制。直白地说: 在能写入该存储的表面之内, 破坏该标记就清除了攻陷证据。界限: 写入路径被限定在 TRUSTED_CONTEXTS 存储内, 所以制造这种损坏需要扩展上下文或下文的冷启动窗口 - 不是网页, 也不是稳态下的内容脚本 - 而固定记录自身的自检 (其密钥 id 必须与其存储的公钥匹配) 是内部一致性, 不是真实性, 但它确实意味着损坏的标记无法伪造或改变固定。
- **受信任存储的冷启动窗口现在也挡在策略状态前面。** 上文 #32 残余风险中已点名的亚毫秒级 `setAccessLevel(TRUSTED_CONTEXTS)` 窗口, 现在也覆盖策略棘轮、切换标志、持久攻陷标记和先前固定记录 (`bridgePolicyPriorPin`)。同样的窗口, 更大的波及范围 - 还有一点与登记门禁的诚实差异: 策略帧在门禁之前路由, 且策略路径自身不等待限制生效, 所以策略状态依赖于限制被尽早应用, 而不是在使用时重新检查。没有用户空间 API 能关闭该窗口。
- **「已固定的扩展拒绝未签名基线」只是已固定情形下的界限。** 在扩展没有固定的机器上, 批准窗口通道在一次新鲜的、明确的用户批准之后接受未签名文档。现在已没有任何主机路径会写入未签名基线, 所以窗口通道自身的让步 (驱动扩展页面的软件可以替它回答提示) 就是全部的暴露面。
- **与 `cdpMode` 吊销竞争的决策可能产生短暂的调试器附加。** 新 CDP 会话的附加在附加后策略重检读取授予之前就已完成, 所以一个快照到 `cdpMode: true` 的进行中决策, 在吊销推送落地之后仍可能附加。该会话上不会发送任何 CDP 命令: 重检会将其拆除并使操作失败 - 诚实的附带说明是, 会话层会吞掉分离错误, 所以拆除是尽力而为的。重检刻意放在附加之后; 在附加前重检曾破坏已固定的附加协议顺序。
- **固定吊销会让存活的 CDP 附加留在原地。** 策略驱动的拆除监听器在存储写入时触发, 而吊销路径刻意保留存储的策略记录 (它是同密钥防重放锚点), 所以没有写入触发, 现有的调试器附加 - 及其横幅 - 会一直留到标签页关闭。分发屏障立即停止所有新工作 (切换之后; 切换之前的扩展没有屏障, 执行的是拒绝基线); 该附加只能滞留, 无法行动。
- **在 Linux 或 Windows 上无法签署任何基线策略。** 唯一的签名密钥是 Secure Enclave 登记密钥, 所以在这些平台上 `policy set` 会预先拒绝, 并保持当前策略不变。没有存储基线时, 不授予任何能力, `policy restrict` 也没有什么可收紧的。

## 重建带来的变化: 新的信任边界

工作区重建引入了六个上文模型中不存在的边界, 现已全部交付。边界 1-3 随中介交付, 边界 4 随桌面应用交付 (该应用已删除; 见下文第 4 项), 边界 5 随 Touch ID 在场门禁交付, 边界 6 随紧急开关交付。每一项都按交付状态描述: 机制、执行点、残余风险。

1. **客户端程序 -> MCP 服务器 stdio 准入 (已交付)。** 服务器不再信任生成它的任何东西。在服务任何一次工具调用之前, 它度量其父进程的代码身份 - `attest_parent()` 取 `getppid()` 并度量该 pid 的运行中映像 (macOS: 经 `SecCodeCheckValidity` 验证的 `cdhash` 加上签名 Team ID; Linux: `/proc/<pid>/exe` 的 SHA256) - 然后对照 `runtime_dir()/trust.json` 信任记录中已配对的客户端进行检查。执行者: MCP 服务器在启动时 (`admit_own_harness`), 以及中介在每次中继接入时再次执行 (中继在 `AttachRequest::Client` 中报告其经证明的父进程身份, 之所以可信, 是因为中继连接本身已通过 `attest_peer`, 因而是我们自己的二进制)。执行与登记仪式一样是选择启用的: 尚无任何已配对客户端意味着未登记, 不执行准入, 每次启动都以 ERROR 级别记录 (先前已有的威胁 #4 同用户残余风险, 未变)。一旦配对了一个客户端, 所有不匹配的都失败即关闭 - 包括无法度量的身份, 也包括不可读或损坏的记录 (加载错误从不被视为未登记)。授权以经证明的锚点为键 (已签名时为代码签名者, 否则为映像哈希); 自我声明的客户端名称 (`CHROMIUM_BRIDGE_CLIENT_NAME`) 只是日志标签。残余: stdio 是没有内核对端凭据的匿名管道, 所以这证明的是谁*生成了*服务器, 而不是谁在写它的 stdin。启动时 `getppid` 指向真正的生成者 (操作系统刚刚 fork 了我们), 之后的重新认父会让它指向收割进程, 从而准入失败即关闭; 但匿名管道的写入端可以被继承或传递, 所以生成者与 stdin 写入者无法被证明是同一个, 而以 pid 为键的度量带有通常的微秒级 pid 复用竞争 (在 macOS 上运行中映像仍经签名验证)。它抬高了门槛; 它不是对管道的内核证明。而且证明识别的是二进制, 不是意图: 受信任但已被攻陷的客户端程序仍然受信任。由对抗性测试 A14/A15/A16 实际演练。

2. **引用计数的中介 (已交付)。** 第一个 MCP 服务器实例绑定 0600 套接字和锁并成为中介; 之后经证明的实例作为中继接入, 而不是向所有者发送 SIGTERM (旧的「最新者胜」`supplant_prior_server` 接管已被移除)。一个共享的 `Session` 持有浏览器连接, 并复用每个已接入客户端程序的工具调用。

   中介按客户端程序客户端计数 (它自己的 stdio 客户端程序加上各中继; 浏览器刻意不计入), 并在最后一个客户端程序脱离时退出。关闭协议经 loom 模型检查 (恰好在归零时关闭, 终局决定之后不再有接入)。

   由中介进程执行: 每次接入都单独经过同用户检查、`attest_peer`、HMAC 握手、一个强制的声明角色的接入帧, 以及 (对中继而言) 白名单判定; 套接字在 0700 运行时目录中保持 0600。

   DoS 姿态: 最多 8 个客户端程序客户端和 16 个不同的浏览器, 最多 32 条处于握手中的连接, 10 秒的握手+接入读取超时 (对已准入、合法空闲的连接清除), 以及逐中继的令牌桶速率限制 (突发 128, 补充 128/秒), 会丢弃泛洪的中继。

   残余: 中介把原本分离的波及范围聚合在一起 (一个进程面向所有客户端), 上限缓解了但没有消除这一点; 它也是单点故障, 其崩溃会让每个已接入的客户端程序收到 EOF (幸存者的重启会选出新的中介, 由混沌测试 C4/C9 演练)。

3. **主机白名单的写入者 (已交付)。** 受信任客户端集合持久化在 `runtime_dir()/trust.json` 信任记录中, 与紧急开关锁存并排: 0600, 在运行时锁下原子写入, 以失败即关闭方式解析 (`deny_unknown_fields`、版本检查、大小上限)。写入者: CLI (`pair-client`、`revoke-client`), 以及扩展通过主机中介的 `client_list` / `client_revoke` 控制帧。`pair-client` 替换同名条目 (重新签名后哈希锚点的重新配对路径); `revoke-client` 即使清空也保留列表 (空列表表示已登记且已锁定, `null` 表示从未配对), 并在递增纪元的同一次原子写入中完成, 因此存活的中介会拒绝被吊销客户端的下一个请求及其重新接入。执行者: 0700 运行时目录上的文件权限、原子写入纪律, 以及在每次准入和会话内请求时对记录的重新读取。残余: 信任记录继承了与 Native Messaging 清单相同的同用户写入者暴露 (威胁 #4 的类别) - 能运行我们 CLI 的同用户进程可以把自己配对进来。删除 `trust.json` 会回到以 ERROR 记录的引导状态: 这是不可消减的同用户残余风险, 因为没有任何用户空间标记能在一个可以删除我们能写的任何文件的写入者面前幸存。

4. **应用作为签发者 (已退役)。** 桌面应用已被删除, 连同其进程内确认下限一起; CLI 是唯一的签发表面, 经由 `core` 的写入路径和上文受在场门禁保护的仪式。

5. **Touch ID 确认表面 (已交付)。** 两个最核心工具 (`page_eval`、`page_upload`) 的确认从页面可触及的 DOM 移到主机侧的 Secure Enclave 用户在场门禁。这为这两个工具关闭了上文「提示条可被其守护的页面击败」的残余风险。执行者: 对已登记密钥的一次 Secure Enclave 签名操作, 其 `kSecAccessControlUserPresence` ACL 强制要求 Touch ID (或登录密码), 没有实时的用户动作就无法完成; 扩展针对其固定的密钥, 在一个在场专用的域上验证所得签名。刻意不用 LocalAuthentication 的 `LAContext.evaluatePolicy`, 经实测它会在没有新鲜用户交互的情况下返回成功, 因此不能证明在场。页面和扩展可以请求该提示, 但无法满足它, 且扩展窗口对这些类型只做显示 (没有「允许」按钮)。残余: 仅限 macOS 且已登记; 其他平台和未登记的 Mac 降级为 DOM 之外、失败即关闭的扩展表面, 它好于页面内提示条, 但不具有同样意义上的不可欺骗性。逐操作 Touch ID 是一个主机持有的策略字段 (`touchIdConfirm`, 默认开启): 选择退出会把这两种类型送回窗口确认, 而这是一种放宽, 本身需要一次签名的、受在场门禁保护的策略写入。提示疲劳是真实的代价, 这也是为什么只有最高风险的工具才路由到这里。

6. **全局紧急开关与审计日志 (已交付)。** 一个锁存 (信任记录 `runtime_dir()/trust.json` 中的 `killed`, 与纪元递增原子地一起翻转) 从任何受信任表面停止所有桥活动: CLI (`kill`)、扩展 (主机中介的 `kill_engage` 控制帧; 扩展的 `kill_release` 已退役 - 主机拒绝它并审计)。在四层独立执行, 因此没有任何单一检查是承重的: 来自每个客户端程序的每次 `tools/call` 都在共享分发器处以稳定的 `BRIDGE_KILLED` 代码拒绝; 中介的监视器在一个节拍内切断每条存活的浏览器连接, 浏览器接入在准入时被拒绝; 在已启用紧急开关时 (或记录不可读时) 启动的原生消息主机从不拨号中介, 只服务控制平面, 这正是让状态、启用和策略拉取保持可达的原因; 扩展自身的门禁在其仅 SW 的镜像上拒绝。解除是明确的, 从不自动, 仅限 CLI, 且需要用户在场证明 (`kill::release` 要求一个只有 `src/packages/core/src/presence/` 能构造的 `PresenceAttestation`): 在已登记的 Mac 上是一次 Secure Enclave Touch ID 触碰; 没有 Enclave 密钥时, 是在真实终端上键入的确认 (管道化的 stdin 被直接拒绝)。硬件拒绝从不回退到下限, 失败或不可用的认证让开关保持启用。两种切换在记录不可读时都拒绝 (从未知状态解除会失败即开放)。与此同时, 每一项安全决策 - 准入、拒绝、显示/允许/拒绝的确认、各表面的吊销、紧急开关切换、工具调用 - 都记录到 stderr 和一个有界的 0600 `audit.log` (严格解析的 JSON 行, 按大小上限轮转), 由 `chromium-bridge audit` 读取, 对于扩展自身的事件则镜像到 #32 之后的有界环形缓冲区, 供只读的选项面板使用。审计日志严格遵循「先决策后记录」, 从不会让决策失败 (失败时丢弃, 并有可见的计数器)。残余: 锁存共享信任记录的同用户写入者暴露 (同用户进程可以解除开关, 正如它可以删除记录一样 - 威胁 #4 的类别); 在场下限 (在没有 Enclave 密钥时使用) 证明的是意图而非硬件 (同用户进程可以驱动 pty), 所以它阻止的是静默的、脚本化的和意外的解除, 而不是那个敌意进程 - 每次解除都连同授权它的阶梯等级一起被审计; 启用有一个有界的亚秒级窗口 (一个监视器节拍) 留给进行中的工作, 随后被切断的套接字将其排空; 审计日志按设计是尽力而为的, 所以损坏的接收端产生的是可见的空缺, 而不是被阻塞的决策。
