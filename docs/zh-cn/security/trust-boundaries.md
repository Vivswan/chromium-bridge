# 信任边界

整个系统横跨三个进程和四个协议跳 (hop)。每一跳都是一道信任边界 - 跨越它的数据都要经过校验和/或认证。本页与[威胁模型](threat-model.md)配套阅读。

```
MCP client --(1)-> Rust MCP server --(2)-> native host --(3)-> extension --(4)-> web page
   (trusted)         (trusted)           (trusted)         (trusted)        (UNTRUSTED)
```

## 边界 1: MCP 客户端 <-> Rust MCP 服务器 (stdio, JSON-RPC 2.0)

- **协议引擎**: 这条边界上的 JSON-RPC/MCP 方言由官方的 `rmcp` SDK 提供服务, 外面套着服务循环自己的行长度上限和解析门禁 (关于信任面的决策见 [rationale.md](./rationale.md#mcp-服务器行为))。
- **信任方向**: 客户端程序 (harness) 只有在被*准入*之后才受信任。这条边界同时承载协议正确性和授权: 一旦存在受信任客户端白名单, 准入就在这里裁决。
- **执行机制 (准入)**: 在服务任何工具调用之前, 服务器先用 `attest_parent()` 对派生它的客户端程序做证明, 再把该身份与信任记录 (`runtime_dir()/trust.json`, 由 `pair-client` / `revoke-client` / `list-clients` 管理) 中已配对的客户端比对。准入以经过证明的锚点 (代码签名者或镜像哈希) 为键, 绝不以客户端自报的名称为键。
- **`attest_parent()` 测量什么**: Unix: 父进程 `getppid()` 所指向的正在运行的镜像 (macOS: 经验证的 `cdhash` + 签名 Team ID; Linux: `/proc/<pid>/exe` 的 SHA256)。Windows: 服务器 stdin 管道的创建者 (镜像 SHA256 + 作为签名者的 Authenticode 发布者), 因为记录在案的父进程在 `CreateProcess` 时可由调用方任选; 管道两端必须指向服务器以外的同一个进程, 否则失败即关闭。
- **准入姿态**: 未登记 (尚无任何客户端配对) 时保持原有的开放姿态, 并以 ERROR 级别记录日志; 一旦有客户端配对, 任何不匹配的情况都失败即关闭, 包括无法测量的身份和不可读的记录。
- **残余风险**: stdin 是匿名管道, 没有内核对端凭据, 所以被证明的一方是*派生*服务器的进程, 而不是向其 stdin 写入的进程。之后的重新认父 (Unix) 会让准入失败关闭, 但由于管道 fd 可被继承, 派生者和 stdin 写入者无法被证明是同一个进程; 这不是对管道的内核证明。这一残余风险的 Windows 形式记录在[威胁模型](threat-model.md#残余风险-已接受已跟踪)中。
- **执行机制 (吊销)**: 准入不是一次性裁决。位于 `runtime_dir()/trust.json` 的信任记录会在会话内每个请求之前重新读取, 这是中介 (broker) 的逐请求准入门禁; 对空闲连接则由监视器按定时器重新读取。因此从任何界面发出的 `revoke-client` 都会以失败即关闭的方式拒绝被吊销客户端程序的下一个请求, 其重新接入也会被拒绝。这些路径上的每一次读取都失败即关闭。删除该记录是[威胁模型](threat-model.md#重建带来的变化-新的信任边界)点名的残余风险。
- **执行机制 (紧急开关)**: 同一份记录还承载全局紧急开关 (kill switch) 的闩锁, 与其纪元递增一起原子写入。闩锁置位期间 (或记录不可读时), 来自每个客户端程序的每一次 `tools/call` -- 中介自己的和每个中继的, 它们共用一个分发器 -- 都在任何路由之前以稳定的 `BRIDGE_KILLED` 分类码应答。客户端程序的连接刻意保持打开, 这样拒绝以带类型的错误送达, 而不是一次不明所以的断连。解除是显式操作 (`unkill` - 绝不经由扩展, 扩展侧的解除路径已退役: 主机拒绝源自扩展的 `kill_release` 并审计该尝试), 需要用户在场证明 (已登记的 Mac 上为 Secure Enclave Touch ID 轻触; 没有 Enclave 密钥时为 CLI 的终端键入确认, 管道化的 stdin 一律拒绝), 且记录不可读时拒绝。两种状态转换都会被审计; 解除事件会记录授权它的认证路径。
- **执行机制 (协议)**: 严格的 JSON-RPC 解析; 未知方法 -> `-32601`; 解析错误会上报而非致命; **stdout 只承载协议** (诊断信息写到 stderr, 否则一次误写就会损坏数据流)。

## 边界 2: Rust MCP 服务器 <-> 原生消息主机 (桥接套接字, NDJSON)

- **信任方向**: 这是唯一一条针对*本地*对端设防的边界 - 任何可能试图触达桥接的进程。
- **所有权**: 这条边界的服务端是**中介**: 第一个绑定套接字和锁的 MCP 服务器实例。之后经证明的实例通过同一个套接字作为中继接入它, 中介把它们各自客户端程序的工具调用复用到一个共享会话中; 浏览器侧的原生消息主机也一并接入。HMAC 握手之后, 每个对端必须立即发送一个声明角色的接入帧 (`AttachRequest`: 浏览器或中继客户端), 读取时失败即关闭; 中继的接入帧还额外携带其经证明的客户端程序身份, 供边界 1 做白名单裁决。中介按客户端程序数量做引用计数, 最后一个脱离时退出; 旧的「最新者胜」接管 (向先前的所有者发 SIGTERM) 已被移除。
- **执行机制**:
  - **无监听端口**: 在 Unix 上, 桥接是一个位于 0700 每用户目录内的 **0600 Unix 域套接字**, 因此没有 localhost 端口可供其他进程连接, 文件系统权限位把其他用户挡在外面。在 Windows 上它是一个命名管道, 其安全描述符只允许当前用户, 内核在打开时就把其他用户挡在外面。
  - **对端 UID 检查** (Unix): 在 `accept` 时, 服务器从内核读取连接方的 UID (`getpeereid` / `SO_PEERCRED`), 在认证之前就丢弃任何不是来自自身 UID 的连接。在 Windows 上, 管道的描述符就是这项检查, 由内核在连接存在之前执行。
  - **由内核证明的可执行文件身份**: 仍在认证之前, 每一端都获取对端的由内核证明的身份, 并要求它与自己正在运行的镜像一致, 因此同一用户的另一个程序在此被拒绝。证明是**双向**的: 服务器在 `accept` 后证明主机, 主机在 `connect` 后证明服务器。
  - **Linux 身份**: 来自 `SO_PEERCRED` 的对端 PID, 然后是 `/proc/<pid>/exe` 的 SHA256 (绑定到正在运行的 inode, 解析时存在一个很窄的 pid 复用竞争)。
  - **macOS 身份**: 对端的内核**审计令牌** (`LOCAL_PEERTOKEN`), 用 `SecCodeCheckValidity` 验证并按 `cdhash` 比对, 绑定到正在运行的镜像, 同时关闭了按路径重新打开的 TOCTOU 和 pid 复用竞争。只有当内核报告不支持审计令牌选项时 (`ENOPROTOOPT`, 较旧的系统), 才回退到按 pid 识别的 `SecCode`, 此时那个很窄的 pid 复用竞争仍然存在; 任何其他错误都失败即关闭。
  - **Windows 身份**: 内核为管道另一端记录的 pid, 然后是该 pid 所运行镜像文件的 SHA256, 按路径重新打开; [威胁模型](threat-model.md#残余风险-已接受已跟踪)记录了这留下的缺口。
  - **HMAC 质询-应答**: 服务器发送一个新鲜的随机 nonce; 主机回复 `HMAC-SHA256(secret, nonce)`, 以常量时间验证。每次运行的密钥 (0600 锁文件) 从不在线路上传输, 每个连接的 nonce 挫败重放。
  - 每个连接都是经过大小检查的 NDJSON; 同一标识下的浏览器重连会替换该标识先前的写入端。中介还限定了这个面: 最多 16 个不同的浏览器标识和 8 个客户端程序, 最多 32 个处于握手中的连接, 握手+接入读取超时 10 s, 以及每个中继的速率限制。
  - **紧急开关**: 闩锁置位期间, 中介的监视器在其一秒的节拍内切断每一条活跃的浏览器连接 (把进行中的调用排空为带类型的失败), 浏览器接入在准入处被拒绝。不可读的信任记录得到同样的处理: 紧急开关状态不可知时, 任何浏览器连接都不得存续。中继保持接入; 它们的调用在边界 1 被以带类型的方式拒绝。
  - **Windows 残余风险**: 镜像是通过按路径重新打开来测量的, 并且持有密钥的锁文件在那里没有显式设置权限位, 而是依赖每用户运行时目录 (`LOCALAPPDATA`, 或 `USERPROFILE\AppData\Local`; 作为最后手段的临时目录不保证按用户隔离; 见 `src/packages/core/src/ipc/` 中的 `runtime_dir()`) 的默认权限。[威胁模型的残余风险](threat-model.md#残余风险-已接受已跟踪)承载前者; 该密钥只是四道门禁之一, 不是唯一一道。
  - **残余风险**: 哈希和代码签名都无法区分由浏览器合法派生的主机和同一用户的攻击者重新运行的同一个二进制: 字节和 cdhash 完全相同。要堵上这一点需要浏览器/扩展侧配对 (扩展设置中的首次使用即信任)。在 macOS 上, 信任固定到一个精确的 cdhash; Team-ID / designated-requirement 固定 (以便同时接受另一个受信任的构建) 是推迟的后续工作, 不是同一二进制桥接中的缺口。

## 边界 3: Chrome <-> 原生消息主机 (Native Messaging 帧格式)

- **信任方向**: Chrome 按主机清单派生主机, 清单的 `allowed_origins` **固定了扩展 ID** - 只有我们的扩展能与之通信。
- **执行机制**: 4 字节小端长度前缀 + JSON; 入站 64 MB 钳制, 出站 1 MB 上限; stdout 单写入端 + 每帧刷新; `panic = "abort"` + stderr panic 钩子, 使 panic 无法损坏帧流。stdin EOF 时关闭。
- **主机处理的控制帧**: 登记仪式、客户端管理交换、紧急开关帧 (`kill_status`/`kill_engage`/`kill_release` -> `kill_status_result`) 以及即发即忘的 `audit_event` 都由主机自己应答, 绝不转发给 MCP 服务器; 同类帧若从服务器一侧到达则作为注入丢弃。`audit_event` 还额外受种类白名单限制 (只允许扩展拥有的确认/登记种类), 且由主机自行标记来源界面, 因此浏览器一侧无法向审计日志伪造主机侧事件。`kill_release` 是唯一会恢复而非削减能力的管理帧, 主机直接拒绝它并审计: 解除是应用/CLI 在在场门禁之后的操作, 扩展只保留启用 (在每个界面上刹车都只需一步, 恢复能力则不然)。紧急开关闩锁置位期间, 主机运行在仅控制平面模式: 它从不拨号中介, 丢弃桥接帧, 并恰好保持这些控制帧可用, 使状态、启用和策略拉取在已关停状态下仍可触达。
- **残余风险 (主机到扩展方向未经认证)**: `allowed_origins` 固定了哪个扩展可以打开主机, 但没有任何东西固定扩展会接受哪个主机。清单位于用户可写的目录中, 因此同一用户的攻击者可以把它的 `path` 改指向一个恶意主机二进制。浏览器启动该二进制, 它直接与扩展说原生消息协议, 绕过边界 2 的已认证套接字。要堵上这一点需要在扩展中做首次使用即信任的主机身份配对。见[威胁模型](threat-model.md)。

## 边界 4: 扩展 <-> 网页 (Chrome API / 内容脚本 / DOM)

- **信任方向**: **页面不受信任。** 这是安全关键的边界。
- **执行机制**:
  - **站点白名单**: 页面级操作只在用户批准过的源 (origin) 上运行; 新的源会提示用户并请求对应的主机权限 (Chrome host permission)。页面无法自我批准。
  - **确认**: 提交/链接点击、`page_press`、`page_select`、`page_eval`、关闭标签页和 `page_upload` 都在扩展拥有的弹出窗口 (`confirm.html`) 上确认, 它是一个运行在自己进程中的 `chrome-extension://` 文档, 页面无法读取、覆盖或自动点击它; 路由器只接受来自该确切文档的就绪/决议消息。超时、关闭和提供者缺失都视为拒绝。只有这些高风险操作需要确认; 低风险操作 (导航、`page_text`、`tab_list`、脱敏的 Cookie 或存储读取) 不做逐操作提示。与打开中的确认窗口竞争的导航, 由与动作原子执行的页内源断言捕获; 点击还额外绑定到已批准的目标描述符。在已登记的 Mac 上, `page_eval`/`page_upload` 的批准经由主机的 Secure Enclave (Touch ID)。
  - **脱敏**: 页面文本、Cookie、存储和 eval 输出在 Service Worker 中 (`egress.ts`) 于回传给模型之前脱敏, 两个页面后端共用这一处。
  - **信任状态隔离 (#32)**: `storage.local` 和 `.session` 通过 `setAccessLevel(TRUSTED_CONTEXTS)` 限定在扩展上下文内, 因此内容脚本无法读写登记的固定项、已泄露标记、强制执行的策略状态 (策略棘轮和切换标志) 或站点白名单。登记门禁在该限制生效之前失败即关闭。残余风险: 异步限制生效之前存在一个亚毫秒级的冷启动窗口 (见威胁模型)。
  - **紧急开关镜像与审计环**: 主机紧急开关状态的仅 SW 可见镜像和扩展的审计环存放在同一片受限存储中。镜像读到已关停、未知或格式错误时, 请求门禁拒绝 (垃圾数据绝不映射到宽松的「缺失」状态); 镜像只由主机的 `kill_status_result` 帧写入, 绝不由运行时消息写入。路由器只接受来自扩展自身页面的 `get_kill`/`set_kill`/`get_audit`, 因此没有任何页面或内容脚本能读取状态、切换开关或读取日志。
  - **隔离**: 内容脚本运行在隔离世界中; `page_eval` 使用 `Function` 构造函数 (而非内容脚本的作用域), 其结果在脱敏之前经过安全序列化 (循环引用/DOM/特殊类型)。两个页面后端运行同一份自包含的 DOM 实现 (`lib/dom/page-api.ts`); CDP 路径传送的是它的字符串化源码, 因此两者不会分叉。
  - **凭据只读**: 不写 Cookie/存储。

## 不得倒退的不变量

- 两种二进制模式下的 stdout = 只有协议字节。
- 桥接绝不服务未通过以下任一检查的连接: 同用户检查 (Unix 上的对端 UID, Windows 上的管道描述符)、可执行文件身份证明、HMAC 握手, 或强制的声明角色的接入帧。
- 一旦存在受信任客户端白名单 (已登记), 除非客户端程序经证明的身份匹配某个白名单锚点, 否则不予服务 -- 无法测量的身份和不可读的白名单都失败即关闭, 客户端自报的名称绝不作为授权键。
- 主机清单的 `allowed_origins` 始终恰好固定为我们的扩展 ID。(这只固定了扩展到主机的方向; 主机到扩展这一跳尚未认证。见边界 3。)
- 任何页面级工具都不会在非白名单的源上运行 (未设置 `allowAllSites` 时)。
- 任何工具都不写 Cookie 或 Web 存储。
- 紧急开关启用期间, 或其记录不可读时, 不服务任何工具调用, 任何浏览器连接都不得存续; 开关只能由受信任界面的显式解除清除, 绝不自动清除。
- 审计日志绝不作为决策的门禁: 记录是先决策后记录, 写入失败会丢弃该条记录 (通过丢弃计数器可见), 而不是让操作在任一方向上失败。

更改上述任何一条都是**安全相关变更** (见 [SECURITY.md](../../../.github/SECURITY.md))。
