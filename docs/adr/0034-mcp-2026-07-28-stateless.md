# ADR-0034: MCP 2026-07-28 (stateless) on the official rmcp SDK

- Status: Accepted
- Date: 2026-08-08
- Supersedes: [ADR-0007](0007-mcp-protocol-version-2025-06-18.md) (the
  `2025-06-18` pin and the hand-rolled initialize-era implementation behind
  it)

## Context

ADR-0007 pinned the MCP protocol version to `2025-06-18` and named its own
re-evaluation trigger: "if MCP releases a new stable version and clients
upgrade, browser-bridge may need a protocol version bump plus adaptation to
the new conventions". That trigger has fired. The MCP spec revision
**2026-07-28** is released, and it adopts the stateless model ADR-0007's
"Alternatives considered" saw as a draft:

- No `initialize` / `notifications/initialized` handshake and no session
  state; each request identifies its protocol version in
  `_meta["io.modelcontextprotocol/protocolVersion"]`.
- `server/discover` is a MUST for servers to implement (calling it is
  optional for clients, which can also learn the supported versions from a
  version error's `data.supported`): it replaces the handshake as the
  discovery mechanism.
- Results carry a `resultType` discriminator.
- Discovery results carry cacheability metadata (`ttlMs`, `cacheScope`).

The implementation context changed with it. ADR-0007's hand-rolled handler
("5 method branches plus the default `-32601`") was the right call when no
Rust library implemented the protocol: minimal, auditable, nothing to trust
but ourselves. The MCP project's official Rust SDK
([rmcp](https://github.com/modelcontextprotocol/rust-sdk)) now ships stable
2026-07-28 support, which expires that justification under this repo's own
rule: prefer many-eyes libraries over homegrown code, even in the security
core, reserving bespoke code for what genuinely has no library.

Two more facts frame the decision:

- **We are a pre-release product.** There is no installed base whose pinned
  behavior we must preserve across releases, so a full migration (rather than
  a long dual-version regime) is available to us cheaply now and only gets
  more expensive later.
- **Claude Code's 2026-07-28 support is still rolling out** (verified
  2026-08-08: the Anthropic blog announcing the revision says support is
  "rolling out"; the Claude Code docs do not yet advertise `server/discover`).
  A server that refuses the old opening today bricks the primary harness that
  spawns it.

The intermediate spec release `2025-11-25` was never adopted here and imposes
nothing on a tools-only stdio server: its input-validation change (invalid
tool arguments surface as tool errors, not protocol errors) matches what we
already do, and its JSON Schema 2020-12 dialect statement is compatible with
the schemas we emit. Skipping it costs nothing.

## Decision

**Rebuild the MCP layer on rmcp, speaking protocol version `2026-07-28`
(stateless), with the SDK's built-in legacy-era support enabled temporarily
for harnesses that still open with `initialize`.**

### The SDK enters the trust surface (a reviewed decision)

The layer uses rmcp 3.x (the `server` feature; the wire stays our own serve
loop, not an rmcp transport) with a small shared tokio runtime (two worker
threads, plus the blocking pool for tool execution) confined to the MCP
serve path. That puts
**rmcp and tokio inside the security core's trust surface**, and this
record is the explicit, reviewed decision the security principles require
for such a change:

- The justification is the many-eyes rule itself. The protocol now has an
  official, widely used SDK maintained by the MCP project; it tracks spec
  revisions and has had more hostile review than a parser we write and fuzz
  ourselves. Bespoke code stays reserved for what has no library (our IPC,
  attestation, and native-messaging protocol - all unchanged).
- Both crates are gated like every dependency: `deny.toml` plus the
  automated dependency review that replaces the cargo-vet gate (ADR-0035).
  The host binary's dependency graph roughly doubles (32 to 63 crates by
  unique name), all green under `cargo deny`. rmcp also brings `schemars`
  (v1) into the shipped host binary's graph for
  its tool-schema model; our own gen-only schemars feature stays out, and
  `moon run check-gen-isolation` pins that rmcp is the ONLY path by which
  schemars may reach the binary.
- Our enforcement invariants stay outside the SDK and wrap it: harness
  attestation and admission pass before serving begins, the kill switch and
  audit trail run on every tool call, all diagnostics stay on stderr
  (stdout is protocol), and the broker/relay legs are untouched.

### Modern era (the target behavior)

- **Per-request version gate.** A modern request carries
  `_meta["io.modelcontextprotocol/protocolVersion"]` and
  `_meta["io.modelcontextprotocol/clientCapabilities"]` (rmcp requires
  both on every stateless request; an empty capabilities object is
  sufficient) and is gated on the version individually. An unsupported
  version STRING is refused with JSON-RPC error `-32022`
  (`UnsupportedProtocolVersionError`) carrying
  `data: {supported: [...], requested: <what the client sent>}` - the
  spec's defined code for exactly this case, with `data.supported` naming
  rmcp's full supported set (below). There is no negotiation and no
  session to fall back on: the gate runs on each request independently.
- **The connection opener is fail-closed.** rmcp accepts as a connection's
  FIRST request only a legacy `initialize` or a well-formed stateless
  request (both `_meta` keys present, the version a string); anything else
  - a bare probe, a partial `_meta`, a non-string version - drops the
  connection without a reply, and the stdio server exits. Two measured
  edges: an unsupported-but-string version in an otherwise well-formed
  opener is answered `-32022` and the connection continues, and a bare
  `ping` is answered `{}` before any opener (the spec allows ping at any
  time) without opening the connection - though after a stateless opener a
  bare `ping` is `-32602` like any other version-less request, and a
  `ping` carrying modern `_meta` is `-32601` (ping is legacy vocabulary;
  only the initialize-opened era keeps answering it).
- **There is no bare `server/discover` form.** The original design planned
  to serve a `_meta`-less probe as a leniency; rmcp has no such form, and
  per the decision recorded at design time the leniency is dropped rather
  than patched in. A client that does not yet know what the server speaks
  learns the supported set from a well-formed `server/discover` or from
  any `-32022` error's `data.supported`.
- **Discover result**: `supportedVersions` is rmcp's full supported set -
  `["2024-11-05", "2025-03-26", "2025-06-18", "2025-11-25", "2026-07-28"]`
  as of rmcp 3.1 - kept deliberately at the SDK default so pre-2026
  harnesses keep negotiating their own revision during the rollout;
  `capabilities: {"tools": {}}`. A unit test pins the newest entry to the
  repo-wide `2026-07-28` pin, so a silent rmcp upgrade that moves the wire
  fails the build instead of drifting past this record.
- **Cache hints on cacheable results.** The `server/discover` and
  `tools/list` complete results carry `ttlMs: 3600000` and
  `cacheScope: "private"` (the spec requires hints on both; the values are
  ours, set on the SDK's results). The hints are stamped only for peers
  whose revision speaks that vocabulary (>= 2026-07-28); pre-2026 peers
  get the exact pre-migration shapes.
- **Results carry `resultType`.**
- **`initialize` is served in every era.** The design intent was to refuse
  a modern-era `initialize` with an error naming `2026-07-28`; rmcp's
  actual behavior - adopted, since the SDK's served behavior is the source
  of truth - is to answer `initialize` wherever it appears as a legacy
  negotiation: a supported requested revision is echoed back, an unknown
  one is answered with the newest supported revision. The e2e suites pin
  the served behavior.

### Served behavior is the SDK's, resolved at integration

The engine is the official SDK, so its served behavior is the source of
truth wherever the spec leaves room, and this record documents actuals
rather than preferences. The protocol e2e suites assert the actual
literals, so drift between this record and the served bytes fails CI
rather than going unnoticed. The two edges recorded as pending at design
time were resolved from the SDK's measured emissions (probed on the wire
and pinned by unit tests in `mcp/connection.rs`):

- **Incomplete or malformed stateless metadata is `-32602`** (Invalid
  params), the spec's letter: in a stateless session, a missing `_meta`,
  an empty `_meta`, a missing `clientCapabilities`, and a NON-STRING
  version value (which decodes as a missing version) all get `-32602`
  with a message naming the missing or malformed field(s). The version
  gate runs before metadata completeness, so an unsupported STRING
  version is `-32022` even when `clientCapabilities` is absent - in
  stateless and legacy sessions alike. In a LEGACY (initialize-opened)
  session an undecodable claim is instead ignored and the request served
  under the negotiated revision - except a decodable `>= 2026-07-28`
  claim, which triggers the full metadata requirement (`-32602` when
  incomplete); both legacy-session behaviors are source-derived from
  rmcp. One parse-order nuance: a `server/discover` with no `params`
  member at all does not decode as a discover request and falls to the
  method catch-all (`-32601`) in a legacy session, while a `params: {}`
  is `-32602`.
- **`clientCapabilities` is required by rmcp on every stateless request**
  (an empty object suffices). This server relies on no client capability
  (tools only: no sampling, elicitation, or roots), so
  `MissingRequiredClientCapability` (`-32021`) still never applies on our
  account; the field's presence is enforced by the SDK's metadata
  validation as part of the `-32602` rule above.

One measured residual is recorded here rather than fixed: rmcp echoes an
unsupported version claim VERBATIM in `-32022`'s `data.requested`, with no
size bound of its own - the only cap is the serve loop's 64 MB line limit.
That is a 1:1 reflection (never amplification); the adversarial suite pins
the non-amplification property, an upstream rmcp issue is the recommended
follow-up (forking the SDK's error shape locally was rejected), and this
note retires if rmcp starts bounding the echo. The seam's own `-32600`
refusal of degenerate frames is
the same class: its detail string comes from serde and can inline a value
from the offending frame, 1:1 and bounded by the same line cap.

Two smaller measured edges, named honestly rather than patched:

- A malformed FIRST frame that decodes as a notification (an `id: null`
  request, say) is swallowed per JSON-RPC, and the rmcp opener ends behind
  it; the connection then idles - the same resource profile as a live idle
  connection - until the peer's next well-formed, service-bound request,
  which reads end-of-service and drops it (frames the seam refuses locally,
  a boolean id say, still get their `-32600` first). Fail closed, one
  request late.
- A `tools/call` whose params are malformed (missing `name`, non-object
  `arguments`) does not decode as a tool call: rmcp refuses it at the
  protocol level (`-32601`) before our handler runs, so no kill-switch
  check and no audit record fire for it. No browser action is possible on
  that path; the audit trail records well-formed tool calls only.

Unchanged by this migration, verified in source rather than live: the
lock-supersede path (a dead broker's lock fails `pid_is_alive`, is removed,
and the socket is unlinked and rebound immediately under the runtime
mutex - `ipc/lockfile.rs`) predates and is untouched by the rmcp layer;
the chaos suite's C7 case (`tests/protocol/chaos.py`) live-fires it.

### Cache fields: why 1 hour, why private

- `ttlMs: 3600000`: the tool catalogue is static per binary (it is compiled
  in; see ADR-0028), so the honest TTL would be "until the binary changes".
  One hour bounds how stale a cached catalogue can be across an upgrade
  without forcing clients to re-discover on every session.
- `cacheScope: "private"`: in the spec's terms this field states whether the
  payload is user-specific, and a compiled-in catalogue identical for all
  users would qualify as `"public"`. But the only thing `"public"` buys is
  shared caches and proxies, which a local, single-user, attested stdio
  server does not have, so we assert the conservative scope and lose
  nothing.

### Legacy-era support (temporary)

On a connection OPENED with `initialize`, requests without the `_meta`
version key are served the previous revisions' behavior - the
`initialize` / `notifications/initialized` / `ping` message set and
legacy-shaped tool results - through **rmcp's built-in earlier-revision
support**, not a custom shim module of ours. `initialize` echoes the
client's requested legacy revision when it is in the supported set
(`2025-06-18`; `2025-11-25` is the revision Claude Code 2.1.226 opens
with) and answers an unknown requested revision with the newest supported
one. The leniency for bare requests is scoped to the opener: after a
STATELESS opener, a version-less request is refused with `-32602` (the
era is otherwise a per-request property - a modern-`_meta` request on an
initialize-opened connection is served the modern shapes, and vice-versa
`"2025-06-18"` carried IN `_meta` is served the legacy result shape).
This keeps the bridge working in Claude Code while its 2026-07-28 support
rolls out, and it is a mode the spec itself sanctions: a server that
wishes to support both legacy and modern clients MAY implement both
behaviors (the versioning page's dual-era compatibility matrix).

The **removal criterion** is observed, not dated: when the harness interop
smoke workflow shows our harnesses opening with `server/discover`, we stop
enabling legacy-era support in a follow-up breaking change. From then on a
version-less request is refused fail-closed, the same posture as an
unsupported version.

### Explicitly not applicable to this server

- **Streamable HTTP** headers, sessions, and OAuth: we are stdio-only; the
  transport-level version header and session machinery have no stdio
  equivalent (the per-request `_meta` field is the stdio-side mechanism).
- **MRTR `input_required`**, the **tasks extension**, and **subscriptions**:
  not implemented, not declared in capabilities.
- **`roots` / `sampling` / client-`logging`**: never implemented here, and
  the revision deprecates them; our diagnostics already go to stderr, which
  is what the spec recommends.
- The old `initialize` result's `serverInfo` has no handshake to live in
  anymore; the revision's replacement is the optional per-result
  `_meta["io.modelcontextprotocol/serverInfo"]` field (a SHOULD).
  Measured: rmcp stamps it on the `server/discover` result ONLY - tool
  results carry no `_meta` - which is a recorded SHOULD-gap on
  non-discover results, accepted rather than patched around the SDK
  (clients that want the identity probe `server/discover`, where it is
  always present alongside `name`/`version`).

## Alternatives considered

### Migrate within the hand-rolled layer

Keep ADR-0007's bespoke handler and teach it the stateless revision.
Rejected under the many-eyes rule: the "minimal and auditable" argument held
only while no library existed. Re-implementing a released spec revision by
hand, next to an official SDK that tracks it, buys audit surface instead of
reducing it, and every future revision would cost another hand migration.

### Strict modern-only (no legacy era)

Refuse anything without the `_meta` version key from day one. Rejected: it
bricks current harnesses. Claude Code today opens with `initialize`, so the
bridge would fail in the primary harness that spawns it for the length of
the rollout, for no security gain (the legacy era serves only the behavior
we shipped yesterday).

### Permanent dual-era support

Keep the legacy era enabled indefinitely. The spec permits this (the same
MAY that sanctions the temporary era), so the rejection is about
maintenance, not conformance: it carries the legacy message set, its tests,
and two-era dispatch forever, for clients that will all move to the
released revision. Legacy support stays only until the removal criterion
above is met.

### Stay pinned to the previous revision

Do nothing until harnesses drop the old opening. Rejected: ADR-0007's
trigger was exactly this release; waiting buys nothing for a pre-release
product and delays `server/discover`, which harnesses are starting to probe
for.

## Consequences

### Positive

- The server speaks the current released revision, and the stateless model
  fits this server's shape: one stdio connection per harness, no session
  state worth negotiating.
- Future spec revisions become an SDK upgrade plus review, not a hand
  migration of a bespoke parser.
- `server/discover` gives harnesses a cacheable catalogue with honest
  cacheability metadata.
- The per-request gate is fail-closed in the modern era: an unsupported
  version is refused on every request, not just at connection start.

### Negative / accepted

- **rmcp and tokio join the security core's trust surface.** Bounded
  deliberately: the runtime is confined to the MCP serve path, our
  enforcement invariants wrap the SDK rather than living inside it, and
  both crates pass the ADR-0035 dependency review like anything else.
  One consequence worth naming: this workspace builds with
  `panic = "abort"`, so a panic inside rmcp or tokio ends the process
  (with the stderr panic hook), not just the connection - the fail-closed
  direction, at availability's expense.
- **Byte-level behavior at malformed-metadata edges is the SDK's**, pinned
  by the protocol e2e assertions rather than by this record; an rmcp
  upgrade can change those literals and will surface as e2e churn.
- **A follow-up breaking change disables the legacy era.** Until then the
  server dispatches across two eras keyed on the opener and the per-request
  presence of the `_meta` version key, and that surface must be tested in
  both eras.
- During the legacy era, a version-less request on an initialize-opened
  connection is served rather than refused, so the modern era's
  fail-closed posture is not yet fully in force. The removal criterion
  bounds this honestly.
- Clients pinned to the previous revision break when legacy support is
  disabled; that is the accepted cost of not carrying the legacy era
  forever, and the removal criterion ensures our own harnesses have moved
  first.
